# 路书 Agent 一期开发计划

> 文档版本：V1.0  
> 文档状态：开发执行稿  
> 更新日期：2026-08-12  
> 开发方式：正式工程 0→1 新建，不迁移、兼容或修补示例代码  
> 关联文档：`requirements/01-路书Agent一期功能需求.md`、`design/02-一期技术方案.md`

## 1. 计划目标

本计划将一期技术方案拆分为可独立验收的开发阶段。每个阶段都必须形成可运行、可测试、可观测的纵向闭环，通过阶段门禁后再进入下一阶段。

一期最终交付的闭环为：

```text
自然语言需求
→ 结构化约束与必要补问
→ 景点推荐与真实 POI 确认
→ 可行的分日路线
→ 天气与地图展示
→ 局部修改与版本保存
→ 固定版本最终页
```

## 2. 开发原则

1. **正式工程从零建立。** 示例代码不是产品代码基线，不承担兼容成本。
2. **先建立业务真相，再建立 Agent。** 数据模型、领域规则、供应商适配器和版本事务优先于完整对话编排。
3. **每阶段先定义评测集和验收门禁。** 不以少量演示成功代替稳定性验收。
4. **LLM 只产生建议和结构化意图。** 坐标、路线、天气、确认状态和版本事实由适配器与领域服务维护。
5. **不确定性必须显式。** 低置信地点、约束冲突、未验证路线和过期天气必须有结构化状态，不得用文案掩盖。
6. **优先完成一期闭环。** 不提前引入 RAG、向量数据库、微服务、复杂 VRP、长期画像和多 Agent 自由协作。

## 4. 阶段 0：基线与评测设计

### 4.1 目标

在写业务功能前统一领域语言、接口合同、状态转移和验收标准，消除需求与技术方案的冲突。

### 4.2 主要任务

- 确认需求与技术方案统一使用“高置信自动采用”规则，候选唯一不单独构成自动采用条件；
- 定义 RouteBook、RequirementSnapshot、Place、ItineraryDay、RouteSegment、Proposal 和 Version Schema；
- 定义 Graph State，禁止将 checkpoint 作为正式业务数据；
- 冻结 REST、SSE 和错误码合同；
- 编写建表、版本事务、中断恢复和幂等性 ADR；
- 建立脱敏的需求语句、POI 候选、路线约束和编辑指令评测集 V1；
- 确定模型版本、Prompt 版本、供应商测试凭证和成本预算。

### 4.3 退出标准

- 需求、技术方案和 API Schema 不存在已知 P0 冲突；
- 核心 Schema 通过评审并可生成 OpenAPI；
- 每个后续阶段都有至少一组正常、歧义和失败验收样本；
- 评测命令可在 CI 中不依赖真实外部服务运行。

## 5. 阶段 1：工程与业务核心

### 5.1 主要任务

- 新建 Next.js、FastAPI、Celery、PostgreSQL、Redis 和 LangGraph Checkpointer 工程；
- 建立分层目录、依赖管理、配置、数据库迁移、代码规范和 CI；
- 实现 RouteBook、WorkflowRun、Proposal 和不可变 Version 的 Repository 与领域服务；
- 实现事务提交、乐观并发、幂等键和统一错误映射；
- 打通 API 创建路书、Worker 执行空工作流和 SSE 进度事件；
- 建立 `request_id / routebook_id / workflow_run_id / version_id` 追踪链路。

### 5.2 退出标准

- 一条 API 请求可创建路书、调度 Worker、推送进度并持久化结果；
- Worker 重投不会重复创建正式版本；
- 并发提交可稳定返回 `VERSION_CONFLICT`；
- 数据库迁移可在空环境一键执行，核心测试进入 CI。

## 6. 阶段 2：外部事实与 POI 质量

### 6.1 主要任务

- 实现高德 POI、地理编码、驾车和步行路线适配器；
- 实现和风天气日预报、小时预报和预警适配器；
- 实现超时、限流、错误码、重试、缓存和 stale 降级策略；
- 建立内部 Place DTO，保留供应商 ID、原始类别、规范类别、地址、行政区和 GCJ-02 坐标；
- 实现 POI 类别映射、主体/入口/交通/商户语义分类、硬过滤和风险词；
- 实现可配置的候选打分与自动采用策略；
- 建立包含重名景区、直通车、车站、停车场、入口、游客中心和同名商户的对抗评测集。

### 6.2 退出标准

- 交通、旅行服务和景区附属设施不会被当作景区主体自动采用；
- 唯一候选但类别不符时进入低置信或无结果流程；
- 适配器契约测试覆盖正常、空结果、超时、限流、鉴权和格式异常；
- 普通 CI 使用脱敏 fixture，少量真实接口测试独立执行且不暴露密钥。

## 7. 阶段 3：需求对话

### 7.1 主要任务

- 定义 `RequirementPatch`、字段来源、置信度、冲突和阻断项 Schema；
- 实现严格结构化输出的 `requirement_extraction` Prompt；
- 实现字段增量合并、已确认值保护、安全默认值和最小输入检查；
- 实现每轮最多 1～3 个阻断问题的澄清节点；
- 实现 LangGraph 中断、持久化、恢复和重复恢复幂等；
- 建立 Prompt 版本、模型输出记录、离线重放和质量评测命令。

### 7.2 退出标准

- 评测集上的必填字段提取达到团队冻结的准确率门槛；
- 模型不把自主推荐写入用户明确需求；
- 用户回答补问后可从原节点恢复，已确认字段不会被无关消息覆盖；
- 结构化输出校验失败有有界修复和澄清降级路径。

## 8. 阶段 4：推荐与地点确认

### 8.1 主要任务

- 实现 `RecommendationStrategy`，输出目标类型、主题权重、地理限制、负面类型和多样性约束；
- 实现多查询召回、POI 硬过滤、偏好打分、去重和多样性选择；
- 推荐地点以 `proposed` 状态保存，附带理由、取舍、来源和评分证据；
- 实现 `PlaceResolutionSubgraph`，区分高置信自动采用、候选消歧、泛指概念偏好选择和无结果澄清；
- 实现推荐接受、拒绝和替换，将拒绝理由作为当前路书重排信号；
- 提供候选名称、类型、地址、行政区、推荐理由和交通取舍的 API DTO。

### 8.2 退出标准

- 所有进入规划的地点都是用户确认或满足完整自动采用策略的真实 POI；
- “长城”“古镇”等泛指概念不会被静默解析为某一具体景区；
- 用户拒绝“太远”后，本路书后续推荐受远郊限制；
- 可观测自动采用率、用户更正率、推荐接受率和拒绝原因分布。

## 9. 阶段 5：行程与路线规划

### 9.1 主要任务

- 建立轻松、适中和紧凑的 `DailyCapacity` 模板；
- 按城市、行政区和坐标分组，优先放入必去地点；
- 实现最近邻和有限 2-opt 的初始顺序优化；
- 对最终相邻地点查询高德正式路线、距离和耗时；
- 实现必去/排除、每日容量、折返、跨区、远郊混排和路线验证检查；
- 实现最多 3 轮的“生成—验证—修复”循环；
- 可修复低优先级推荐项和顺序，不可静默删除必去地点；
- 并行查询天气与预警，组装草稿并执行完整性检查。

### 9.2 退出标准

- 1～7 天、3～15 个地点的测试集能稳定生成连续行程；
- 用户必去和排除约束全部满足，不可满足时输出结构化冲突；
- 正式距离和耗时只来自路径适配器；
- 修复循环在上限内收敛或明确返回不可行；
- 路线或天气部分失败时保留有效地点安排，并正确标记降级状态。

## 10. 阶段 6：编辑、提案与版本

### 10.1 主要任务

- 实现增加、删除、替换地点和修改指定日期的 `EditIntent`；
- 解析“第二天”“这个地点”等引用，无法唯一解析时中断澄清；
- 计算受影响日期、地点、路线段和天气位置；
- 对删除必去、修改多日、改变总天数或主要路线创建待确认提案；
- 只重算最小影响范围，对未受影响日期比较规范化哈希；
- 使用不可变快照提交新版本，实现撤销和暂停期间的版本冲突检测。

### 10.2 退出标准

- 修改第二天时，不受影响日期的规范化哈希保持不变；
- 未确认的重要修改不会覆盖当前正式版本；
- 中断期间基础版本变化时拒绝旧提案提交；
- 撤销创建新版本而非删除历史；
- 重试不会重复提交版本或提案。

## 11. 阶段 7：产品界面与最终页

### 11.1 主要任务

- 实现对话、需求摘要、分日行程和高德地图三栏布局；
- 实现 SSE 生成进度、断线重连、中断问题和提案确认交互；
- 实现行程与地图标记联动、分日路线和验证状态展示；
- 展示推荐理由、取舍、候选类型和用户拒绝入口；
- 实现版本查看、修改摘要、撤销和冲突提示；
- 实现最终完整性检查和绑定指定版本的固定布局分享页；
- 处理移动端、加载、空状态、错误状态和基础无障碍。

### 11.2 退出标准

- 用户可从一句话完成初稿、消歧、局部修改和最终页生成；
- 地图、行程、路线和天气读取同一版本快照；
- 页面明确区分 `verified / unverified / stale / unavailable / proposed`；
- 分享页不会被后续草稿修改静默覆盖；
- Playwright 覆盖一期核心用户路径。

## 12. 阶段 8：稳定性与发布

### 12.1 主要任务

- 执行领域、Graph、适配器、API、前端和 E2E 全量测试；
- 执行 Worker 重启、外部接口超时、Redis/PostgreSQL 短暂失败和重复任务演练；
- 校准 Prompt、POI 打分和自动采用阈值，冻结发布版本；
- 设置 API/LLM/供应商调用限额、超时、告警和成本监控；
- 执行凭证、日志脱敏、分享 token、住宅地址隐藏和依赖安全检查；
- 编写部署、回滚、数据备份、故障恢复和人工重试手册；
- 使用脱敏真实场景做小范围试用，记录更正、拒绝和失败样本。

### 12.2 发布门禁

- 一期端到端验收场景全部通过；
- 不存在 P0/P1 未关闭缺陷；
- POI 错误自动采用、必去遗漏、排除误入和版本静默覆盖为零容忍项；
- 核心 API 和 Graph 节点达到团队冻结的可用性与 P95 耗时目标；
- 成本、限流、失败率、用户更正率和修复不收敛率具备监控和告警；
- 部署、回滚、备份和重启恢复已演练。

## 13. 跨阶段工作流

### 13.1 质量与评测

每完成一个节点或领域服务，同步交付：

- 单元测试和边界测试；
- 脱敏 fixture 或供应商响应样本；
- 结构化日志、指标和错误码；
- 幂等、重试和失败恢复测试；
- Schema 与 API 文档；
- 对应阶段评测集的新增回归样本。

### 13.2 Prompt 发布流程

Prompt 必须经过：

```text
版本化修改
→ Schema 校验
→ 离线评测
→ 与当前版本差异对比
→ 成本与延迟对比
→ 小流量验证
→ 发布或回滚
```

不在生产环境直接编辑未版本化 Prompt。模型升级与 Prompt 修改分开评估，避免无法定位质量变化来源。

### 13.3 Definition of Done

任何功能只有同时满足以下条件才视为完成：

- 功能行为与需求编号和 Schema 一致；
- 领域规则不依赖 Prompt 文案暗示；
- 正常、边界、降级和重试测试通过；
- 数据库写入具备事务、幂等和并发保护；
- 错误对用户可解释，对系统可追踪；
- 不记录供应商密钥和未脱敏敏感信息；
- 相关文档、评测集和运维说明同步更新。

## 14. 阶段依赖与并行策略

```text
阶段 0
  ↓
阶段 1 ───────────┐
  ↓                    │
阶段 2 → 阶段 3 → 阶段 4 → 阶段 5
  │                    │        ↓
  └→ 前端 Mock API 并行 ───┘      阶段 6
                                      ↓
                                    阶段 7
                                      ↓
                                    阶段 8
```

可并行工作：

- 阶段 1 合同冻结后，前端可基于 Mock API 开发基础布局和状态组件；
- 阶段 2 中，POI、路线和天气适配器可并行实现；
- 阶段 3 中，Prompt 评测与 LangGraph 节点可通过假 LLM 并行；
- 阶段 5 中，启发式算法、路线适配和可行性测试可并行；
- E2E 用例从阶段 3 开始逐阶段增加，不等到发布前集中补写。

## 15. 一期之后的逐步优化

以一期真实指标决定优化顺序，不预设必须引入某项复杂技术。

### 15.1 质量优化

- 用户更正率高：扩充 POI 类别映射、评测集和评分特征；
- 推荐接受率低：增加景点知识源、人群标签和建议游玩时长；
- 路线修复率高：改进初始分组、日容量和距离矩阵缓存；
- 需求提取不稳定：扩充语料、分离特定意图 Prompt 或对高难样本升级模型。

### 15.2 能力扩展

- 景点开放时间、预约和建议游玩时长；
- 酒店与每日起终点联动；
- 公共交通、跨城铁路和航班约束；
- 用户授权的长期偏好和多人偏好协调；
- 多来源景点知识库与可追溯推荐证据；
- 当地点数量、跨城规模和约束复杂度足够高时，再评估 OR-Tools 或 VRP 求解器。

### 15.3 工程优化

- 根据真实负载调整 Celery 队列、并发和缓存 TTL；
- 建立 Prompt 和候选评分的线上对比实验；
- 对高成本节点增加语义缓存或小模型路由；
- 在模块边界和团队规模真正需要时，再考虑拆分服务。

## 16. 交付里程碑

| 里程碑 | 对应阶段 | 业务结果 |
| --- | --- | --- |
| M0 工程基线 | 0～1 | 可创建路书并可靠执行工作流 |
| M1 可信地点 | 2～4 | 用户需求可转换为经确认的真实地点集 |
| M2 可行初稿 | 5 | 可生成带真实路线与天气状态的分日行程 |
| M3 可编辑路书 | 6 | 支持局部修改、提案、版本和撤销 |
| M4 一期候选发布 | 7～8 | 用户可完成对话到固定分享页的全闭环 |
