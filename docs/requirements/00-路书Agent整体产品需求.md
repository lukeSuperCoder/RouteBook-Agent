# 路书 Agent 整体产品需求

> 文档版本：V0.1
> 文档状态：需求初稿
> 更新日期：2026-08-07
> 适用阶段：产品立项、中长期规划、完整产品需求评审
> 说明：本文描述产品完整能力，不作为一期开发范围；一期交付以《路书 Agent 一期功能需求》为准。

## 1. 文档目的

本文档用于明确路书 Agent 的产品定位、用户对象、业务流程、功能范围、业务规则及验收要求，作为后续产品原型、交互设计、技术方案和项目排期的需求依据。

本文档重点描述“系统需要提供什么能力”，暂不重点展开模型选型、Agent 框架、数据库、地图引擎及接口实现方式。

## 2. 产品概述

### 2.1 产品名称

暂定名称：路书 Agent（RouteBook Agent）。

### 2.2 产品定位

路书 Agent 是一款面向旅游和出行路线规划的垂直 Agent 应用。

用户通过自然语言与 Agent 反复交流，逐步提供出行需求、补充约束、选择方案并确认具体安排。系统在交流过程中持续查询必要资料、完善路线内容，并不断更新结构化路书配置。最终形成一份完整、可执行、可修改、可视化的地图路书页面。

产品的核心不是“一次性生成一段行程文本”，而是：

> 以对话驱动路书持续构建，以结构化路书数据承载当前结果，以地图页面实时呈现规划进度。

### 2.3 核心产出

一次完整规划应形成以下产出：

- 已确认的出行需求和约束；
- 按日期或阶段组织的完整行程；
- 地点、路线、住宿、餐饮、交通等路书内容；
- 距离、耗时、费用和风险提示；
- 重要信息的来源及有效性说明；
- 可持续修改和版本化保存的路书配置；
- 包含地图、路线和行程时间轴的路书页面；
- 可分享或导出的最终路书。

## 3. 产品目标

### 3.1 用户目标

- 用户不需要掌握专业路线规划方法，通过对话即可逐步形成行程。
- 用户可以从模糊想法开始，不必一次提供全部信息。
- 用户能够清楚知道系统已经理解了什么、还缺少什么。
- 用户能够确认、否决或修改 Agent 提出的安排。
- 用户可以针对某一天、某个地点或某项约束进行局部调整。
- 用户始终能够看到当前版本的路书和地图效果。
- 最终结果应当是可执行的路书，而不是泛泛的旅行建议。

### 3.2 产品目标

- 建立从需求收集到路书生成的完整闭环。
- 将多轮对话稳定转化为结构化路书内容。
- 支持需求细化、方案确认、局部修改、撤销和回溯。
- 在自动规划和用户控制之间建立清晰边界。
- 通过完整性检查和冲突检查提高路书可用性。
- 为后续接入更多数据、工具、导出格式和协作能力保留空间。

### 3.3 非目标

首期产品不以以下能力为主要目标：

- 替代专业的实时驾驶导航；
- 对高风险登山、穿越和极限户外活动提供安全保证；
- 在未经用户单独授权的情况下自动下单或支付；
- 保证所有价格、余票、营业时间等外部数据绝对实时；
- 首期实现复杂的多人实时协同编辑；
- 覆盖所有国家和地区的全部旅行数据。

## 4. 目标用户

### 4.1 自由行用户

希望规划城市游、跨城游、周末游、亲子游或境外旅行，需要获得包含景点、交通、住宿和每日安排的完整方案。

### 4.2 自驾出行用户

关注路线连续性、每日驾驶时间、道路状况、补给、住宿位置、停车、充电或加油以及天气风险。

### 4.3 骑行及其他路线型用户

关注每日里程、海拔、补给点、天气、安全风险和分段安排。专业高风险路线不属于首期重点范围。

### 4.4 商务出行用户

需要围绕航班、车次、会议、客户地点和酒店安排时间可行的路线。

### 4.5 旅行内容生产者

需要快速形成标准化路书、地图展示和可分享内容，并在初稿基础上反复编辑。

## 5. 核心概念

### 5.1 路书

路书是一次出行规划的完整业务对象，包括需求、日期、地点、交通、路线、活动、住宿、费用、风险、资料来源和页面展示信息。

### 5.2 路书配置

路书配置是系统内部持续维护的结构化数据，是当前路书内容的唯一有效业务事实。对话、地图和行程页面均围绕该配置工作。

### 5.3 变更提案

当 Agent 建议的调整会明显影响用户已经确认的路线、时间、预算或预订事项时，系统先形成待确认的变更提案。用户确认后，变更才进入正式路书。

### 5.4 路书版本

每次有效变更形成一个新版本。版本应记录修改内容、修改原因、触发来源和时间，供比较、撤销和回溯使用。

### 5.5 锁定项

用户可以锁定已确定的日期、地点、住宿、交通或行程段。Agent 不得在未提示用户并获得确认的情况下修改锁定内容。

### 5.6 当前路书与最终路书

- 当前路书：规划过程中持续更新、可能仍有缺失或待确认事项的版本。
- 最终路书：通过最终完整性检查并由用户确认生成的发布版本。

最终路书仍可继续修改，但后续修改应生成新的草稿版本，不直接覆盖已经发布或分享的版本。

## 6. 典型用户场景

### 6.1 从模糊想法开始规划

用户提出“国庆想从武汉自驾去川西，大约七天，不想太赶”。系统识别已有条件和缺失条件，分批询问人数、准确日期、车辆、每日驾驶上限、预算及必去地点，并逐步形成路书。

### 6.2 根据明确条件直接生成初稿

用户提供出发时间、目的地、人数、交通方式、预算和必去地点。系统仅补问阻碍规划的关键信息，然后生成可预览的初步路书。

### 6.3 局部修改某一天

用户提出“第二天太赶，减少一个景点”。系统识别受影响日期，调整该日安排，并检查对住宿、后续出发时间和整体路线的连锁影响。

### 6.4 替换地点或住宿

用户提出“不要这个酒店，换到泉州市区”。系统提供替换方案，说明时间、距离和预算变化，用户确认后更新路书。

### 6.5 外部条件变化后重规划

用户提出“明天下雨，把户外项目换掉”。系统更新相关资料，识别受影响的活动，为对应日期提供替代安排，而不重做整份路书。

### 6.6 最终确认与发布

用户提出“就按这个方案生成最终路书”。系统执行最终检查，提示尚未解决的问题，经用户确认后生成最终版本和完整路书页面。

## 7. 总体业务流程

1. 用户创建一次新的路书规划。
2. 用户通过对话描述初始需求。
3. 系统识别需求、约束、偏好及不确定内容。
4. 系统创建路书草稿并展示当前完成度。
5. 系统按优先级向用户补问关键问题。
6. 用户回答问题或主动增加、修改要求。
7. 系统查询规划所需资料并更新候选内容。
8. 系统生成或更新按天组织的行程方案。
9. 对影响较大的调整，系统展示变更影响并请求用户确认。
10. 确认后的内容写入当前路书并形成新版本。
11. 路书页面根据变更内容同步更新。
12. 系统持续检查需求完整性和行程冲突，并推荐下一步需要确认的事项。
13. 用户确认最终生成后，系统执行完整性检查。
14. 检查通过后生成最终路书页面，供查看、保存、分享或导出。

## 8. 功能需求清单

- P0：MVP 必须具备，缺失将无法形成核心闭环；

- P2：增强能力，可在后续版本迭代。

## 9. 关键业务规则

### 9.1 路书为核心业务事实

- 对话内容用于理解用户意图，但当前有效路书以结构化路书配置为准。
- 地图页面和行程页面必须基于同一份路书版本展示。
- 尚未确认的重要建议不得直接覆盖当前有效路书。

### 9.2 信息状态规则

路书中的重要内容应至少区分以下状态：

- 用户已明确；
- 用户已确认；
- Agent 推断；
- 使用默认值；
- 待用户确认；
- 已查询验证；
- 尚未验证；
- 数据可能过期；
- 存在冲突；
- 用户已锁定。

### 9.3 确认规则

以下变更原则上必须确认：

- 删除或替换用户已确认的地点；
- 改变出发日期、结束日期或总天数；
- 改变跨城路线或主要交通方式；
- 影响多个行程日；
- 影响已安排住宿、交通或预约事项；
- 导致预算或行程强度明显变化；
- 修改用户锁定内容；
- Agent 因冲突主动舍弃用户要求。

### 9.4 局部更新规则

- 系统应定位用户修改所影响的最小范围。
- 不受影响的确认内容应尽量保持不变。
- 局部修改完成后，需要检查直接关联内容和后续依赖。
- 如果局部修改导致全局方案无法成立，系统应说明原因并请求用户决定。

### 9.5 提问规则

- 优先询问不回答就无法继续规划的问题。
- 其次询问会显著改变路线、预算或安全性的问题。
- 每轮问题应尽量少而清晰，并说明询问原因。
- 已获得明确答案的问题不得无原因重复询问。
- 用户可以选择暂时跳过，系统应说明跳过后的影响。

### 9.6 版本规则

- 每次被接受的有效修改产生新版本。
- 未确认提案不产生正式路书版本。
- 每个版本应可追溯到触发它的用户表达或系统修复原因。
- 撤销操作本身也应留下记录。
- 最终版和已经分享的版本不得被后续草稿静默覆盖。

### 9.7 最终完成规则

路书进入最终状态前至少应满足：

- 出发和结束安排明确；
- 日期及每日行程连续；
- 主要地点具备有效位置；
- 主要路线可以衔接；
- 必去及排除约束得到处理；
- 没有未解决的阻断冲突；
- 没有未处理的重要确认提案；
- 关键假设和风险已向用户展示；
- 页面能够正确呈现对应版本。

## 10. 路书状态

一份路书可处于以下业务状态：

| 状态 | 含义 |
| --- | --- |
| 草稿 | 已创建，但基础信息尚不足。 |
| 需求细化中 | 正在通过对话收集和确认需求。 |
| 规划中 | 正在查询资料或生成路线。 |
| 待用户确认 | 存在需要用户决策的方案或变更。 |
| 完善中 | 已有可用初稿，正在进行局部调整。 |
| 待最终检查 | 用户已基本确认，准备执行完整性检查。 |
| 存在阻断问题 | 当前无法生成有效最终版，需要继续处理。 |
| 已完成 | 最终版本已生成。 |
| 已发布 | 最终页面已生成并可分享。 |
| 已归档 | 当前不再编辑，但历史内容保留。 |

## 11. 页面与交互要求

### 11.1 主要界面区域

首期页面建议包含以下区域：

- 对话区：展示交流、补问、方案说明和确认操作；
- 需求摘要区：展示已确认条件、缺失条件和完成度；
- 行程区：按天展示时间轴、地点、交通和活动；
- 地图区：展示地点、分日路线和选中对象；
- 提示区：展示待确认事项、冲突、风险和数据状态；
- 版本区：展示最近修改，支持撤销或查看差异。

### 11.2 反馈要求

- 用户发送修改要求后，应立即反馈系统理解的修改目标。
- 资料查询或规划耗时较长时，应显示当前进度。
- 更新完成后，应高亮本轮发生变化的内容。
- 页面应清晰区分正式内容和待确认预览内容。
- 系统无法完成时，应说明原因和可继续采取的操作。

### 11.3 多端要求

- 桌面端应支持同时查看对话、行程和地图。
- 移动端可以使用对话、行程、地图三个页签切换。
- 关键确认操作在移动端必须易于发现和操作。

## 12. 非功能需求

### 12.1 易用性

- 用户可以从一句模糊描述开始，不要求先填写复杂表单。
- 重要概念和状态应使用普通用户能理解的语言。
- 关键变更应明确展示“改了什么”和“会影响什么”。

### 12.2 一致性

- 对话反馈、需求摘要、行程列表、地图和最终页面应基于同一路书版本。
- 同一地点、时间和费用在不同页面不得出现无说明的不一致。

### 12.3 可解释性

- 重要推荐应说明推荐原因。
- 重要事实应能够查看来源或验证状态。
- 系统应清楚区分事实、估算、推断和建议。

### 12.4 可靠性

- 失败不得导致已确认路书内容丢失。
- 页面生成失败不应破坏有效路书配置。
- 系统恢复后应能够从最近有效状态继续。

### 12.5 性能体验

- 普通对话应尽快反馈已接收和正在处理。
- 长时间查询或规划应显示阶段性进度。
- 路书局部修改后，页面应优先更新受影响部分。
- 用户不应因页面刷新而丢失当前对话或编辑状态。

### 12.6 安全与隐私

- 用户敏感信息不得出现在公开分享页面中，除非用户主动选择。
- 系统引用的外部信息应视为可能不准确或过期，并保留必要提示。
- 涉及预订、支付或对外发送信息的操作，应获得单独明确授权。

## 13. 一期功能范围参考

> 本节为整体需求中的早期范围建议。当前一期开发基线以 `01-路书Agent一期功能需求.md` 为准；两者冲突时以后者为准。

### 13.1 MVP 必须包含

- 创建和保存路书；
- 多轮对话收集需求；
- 需求结构化、缺失识别和主动补问；
- 当前需求摘要与完成度；
- 地点和基础路线资料查询；
- 按天生成多日行程；
- 通过对话增加、删除、替换地点及调整某一天；
- 重要变更的预览和用户确认；
- 路书配置持续更新和版本记录；
- 基础时间、距离、必去项和排除项检查；
- 失败后保留有效路书并允许继续；
- 地图、路线和每日时间轴页面；
- 页面随路书变更同步更新；
- 最终检查及最终版本生成。

### 13.2 MVP 可简化内容

- 预算只提供分类估算，不要求实时精确价格；
- 天气、酒店和交通班次可先覆盖有限数据源；
- 多方案对比可以只支持两个方案；
- 导出先支持 HTML 或打印，暂不要求多种文件格式；
- 用户偏好先只在单次路书中生效；
- 首期不提供多人实时协作。

### 13.3 MVP 不包含

- 自动购买机票、车票、酒店和门票；
- 自动支付；
- 实时导航；
- 复杂团队权限和审批；
- 专业探险路线安全决策；
- 完整的旅行内容社区。

## 14. 一期验收参考

### 14.1 核心闭环验收

1. 用户可以从一句自然语言需求创建路书。
2. 系统能够识别已知条件和至少一项缺失的关键条件。
3. 用户回答补问后，需求摘要和路书配置同步更新。
4. 系统能够生成一份按天组织的可视化行程初稿。
5. 初稿能够在地图上显示主要地点和路线。
6. 用户可以通过对话要求修改某一天或替换某个地点。
7. 系统能够展示该修改的主要影响。
8. 需要确认的修改在用户确认前不会覆盖当前正式内容。
9. 用户确认后，行程、地图和相关统计同步更新。
10. 修改应产生可识别的新版本，且能够查看本轮变化。
11. 用户可以撤销至少最近一次有效修改。
12. 用户请求最终生成时，系统能够完成检查并指出阻断问题。
13. 检查通过后，可以生成与最终路书版本一致的完整页面。

### 14.2 可靠性验收

- 单个资料查询失败时，已经确认的行程仍然存在。
- 修改某一天时，未受影响的行程日不会无原因改变。
- 系统不会在未提示的情况下修改用户锁定内容。
- 页面生成失败后，用户仍可继续编辑有效路书。
- 所有未验证和过期信息在页面中有明确状态提示。

### 14.3 体验验收

- 用户能够随时看到当前路书完成到什么程度。
- 用户能够理解 Agent 当前为什么提问。
- 用户能够判断页面中哪些内容已确认、哪些仍待确认。
- 用户能够理解一次修改影响了哪些日期或内容。
- 用户无需重新描述整份需求即可进行局部调整。

## 15. 后续待确认事项

以下事项需要在后续需求评审和原型阶段进一步确认：

1. 首期重点支持的出行类型：城市自由行、自驾或二者同时支持。
2. 首期覆盖的国家、地区和地图数据范围。
3. 是否允许用户直接在行程页面拖拽编辑，还是首期只通过对话修改。
4. 最终路书的分享权限、有效期及是否需要登录查看。
5. 首期必须接入的资料类型及数据准确性要求。
6. 预算、酒店、天气和交通班次在 MVP 中的具体深度。
7. 路书完成度的计算维度与权重。
8. 哪些修改可以自动应用，哪些必须明确确认。
9. 最终版生成后继续修改时的版本和发布策略。
10. HTML、PDF、图片或其他导出形式的优先级。

## 16. 产品原则总结

1. **对话是输入方式，不是最终产物。** 最终产物是结构化、可执行、可视化的路书。
2. **路书配置持续演进。** 每轮有效交流都可能补充或修改当前路书。
3. **重要修改先确认。** Agent 可以主动建议，但用户保留关键决策权。
4. **尽量局部更新。** 修改局部内容时，保持其他已确认内容稳定。
5. **页面持续可见。** 用户在规划过程中随时能够看到当前路书，而不是只在结束时看到结果。
6. **结果必须可检查。** 对时间、路线、约束和缺失项进行明确校验。
7. **失败可以恢复。** 查询、规划或渲染失败不得破坏已有有效路书。
8. **事实与推断分开。** 来源、估算、默认值和不确定信息应清楚标记。
