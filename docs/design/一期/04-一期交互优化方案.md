# 路书 Agent 智能规划工作台交互与实时化优化方案

> 文档版本：V1.0  
> 文档状态：实施方案  
> 更新日期：2026-08-17  
> 适用范围：Web 规划工作台、需求对话、推荐选择、行程生成与进度反馈  
> 关联文档：`requirements/01-路书Agent一期功能需求.md`、`design/02-一期技术方案.md`、`design/03-一期开发计划.md`

## 1. 文档目的

本文针对当前路书工作台在布局、需求确认、任务反馈和阶段呈现方面的问题，给出可直接拆分开发任务的优化方案。

本轮优化的核心不是简单调整三栏比例，而是将当前“对话、行程、地图同时出现”的结果页结构，重构为阶段驱动的智能规划工作台：

```text
提出旅行想法
→ 理解并确认需求
→ 推荐与选择地点
→ 编排和验证路线
→ 展示完整行程
→ 按需查看地图
→ 修改并生成最终路书
```

本文重点定义：

- 工作台布局及地图出现时机；
- 多轮需求确认规则和问题呈现方式；
- 右侧任务面板在不同阶段的内容；
- 前后端统一的规划阶段与进度模型；
- SSE 事件恢复和异步任务反馈方案；
- 分阶段实施计划、测试范围与验收标准。

## 2. 当前问题

### 2.1 地图过早占用核心空间

当前工作区固定显示对话、行程、地图三栏。地图在尚无地点和路线时仍占用约三分之一宽度，只能展示空状态，压缩了需求确认、推荐选择和路线编辑所需空间。

地图属于路线形成后的验证与浏览工具，不属于需求澄清阶段的常驻工作区。

### 2.2 后端具备补问循环，前端仍按普通消息展示

当前需求工作流已经具备 `extract → merge → clarify → interrupt → resume` 循环，但前端只是将 `questions[].prompt` 拼接成文本消息，未表现出：

- 当前缺少哪些关键条件；
- 哪些条件已经确认；
- 问题应使用日期、单选、多选还是自由输入；
- 用户是否可以选择“暂不确定”或“不考虑该项”；
- 回答后下一阶段是什么。

### 2.3 需求阻断规则过于刚性

当前出发地、具体开始日期、天数和交通方式均被视为必填阻断项，不支持以下合理需求：

- 只规划目的地内部行程，不考虑往返；
- 只确定月份，具体日期稍后决定；
- 以公共交通、打车或混合交通游览城市；
- 用户授权系统对普通偏好采用建议默认值。

### 2.4 任务开始后反馈不及时

发送消息后，前端主要依赖 `busy` 和顶栏的一行进度文本。用户消息、AI 接收反馈和右侧工作状态不会立即出现。推荐生成和行程生成仍是同步 HTTP 请求，执行期间缺乏分阶段反馈。

### 2.5 SSE 存在事件丢失窗口

当前进度使用 Redis Pub/Sub。服务端可能在前端拿到 `workflow_run_id` 并建立 `EventSource` 之前发布事件，早期事件不能回放。断线重连后也无法根据 `Last-Event-ID` 恢复遗漏进度。

### 2.6 右侧面板没有任务阶段语义

当前右侧始终以“分日行程”呈现。没有路线时显示空行程，有推荐时继续堆叠推荐列表，完成后再显示路线。这使需求确认、地点选择、路线生成和结果查看缺少清晰边界。

## 3. 优化目标与原则

### 3.1 产品目标

1. 用户发送任何有效输入后，100 毫秒内看到本地反馈。
2. 用户在任何时刻都能知道系统正在做什么、需要自己做什么、下一步是什么。
3. 每轮只询问当前最重要的少量问题，避免一次性表单审问。
4. 右侧始终呈现当前任务，而不是提前展示最终结果容器。
5. 只有形成可浏览路线后才加载和展示地图。
6. 进度断线或刷新后能够恢复，不依赖瞬时事件。
7. 展示可解释的工作过程，但不暴露模型隐藏思维链。

### 3.2 设计原则

- **阶段优先**：界面由业务阶段决定，而不是由某个数组是否为空临时推断。
- **渐进确认**：先确认会改变整体规划的问题，再询问普通偏好。
- **可跳过但不含糊**：区分未提供、明确跳过、系统建议和用户已确认。
- **先反馈后执行**：发送后立即进行乐观展示，再异步同步服务端结果。
- **状态可恢复**：页面刷新、SSE 重连和 Worker 重试后均能恢复当前阶段。
- **事实与建议分离**：用户需求、系统建议、供应商事实和路线结果使用不同状态。
- **地图按需加载**：避免在需求阶段初始化高德地图及相关 SDK。

## 4. 目标交互流程

### 4.1 主流程

```text
用户输入旅行想法
        ↓
系统立即回显并进入“正在理解”
        ↓
抽取已知条件并判断缺口
        ├── 有阻断问题 → 分轮确认 → 继续抽取
        └── 条件足够
                ↓
          展示需求确认摘要
                ↓
          生成地点推荐
                ↓
          用户接受、拒绝或替换候选
                ↓
          编排行程并验证路线
                ↓
          展示完整分日行程
                ├── 查看地图
                ├── 对话修改
                └── 生成最终页
```

### 4.2 示例对话

用户：

> 规划 9 月份北京三日游。

系统识别：

- 目的地：北京，已确认；
- 时间：9 月，精度为月份；
- 天数：3 天，已确认；
- 出发范围：待确认。

第一轮问题：

> 这次需要把出发地和往返交通也规划进去吗？

选项：

- 只规划北京市内行程；
- 包含往返，我来填写出发地。

用户选择“只规划北京市内行程”后，系统不再追问出发地，继续询问：

> 北京市内希望以什么方式移动？

选项：

- 地铁和步行为主；
- 打车为主；
- 自驾；
- 由你根据路线安排。

随后再确认路线节奏和主要兴趣。普通偏好允许用户选择“由你推荐”，由系统生成带原因的建议默认值。

## 5. 工作台信息架构

### 5.1 默认布局

规划阶段使用双栏布局：

```text
┌──────────────────────────────────────────────────────────┐
│ 顶栏：旅行标题 │ 当前阶段 │ 撤销/历史/最终页            │
├─────────────────────┬────────────────────────────────────┤
│ 对话区 36%～42%      │ 任务面板 58%～64%                 │
│                     │                                    │
│ 对话记录             │ 需求确认                           │
│ AI 工作反馈          │ / 推荐选择                         │
│ 快捷回答（可选）     │ / 路线生成进度                     │
│ 输入框               │ / 完整分日行程                     │
└─────────────────────┴────────────────────────────────────┘
```

宽屏建议使用 `minmax(320px, 0.72fr) minmax(540px, 1.28fr)`；中等屏幕保持双栏但降低左栏最小宽度；移动端改为单栏，并通过顶部阶段导航或粘性任务摘要在“对话”和“规划”间切换。

### 5.2 地图展示

地图满足以下条件后才允许打开：

- 至少存在一个已生成的 `days_plan`；
- 当前日期至少包含一个具有有效坐标的地点；
- 当前查看的版本或提案快照明确。

桌面端建议使用右侧大抽屉或工作区视图切换：

```text
[行程] [地图]
```

地图打开后：

- 宽度不少于视口的 60%；
- 保留日期切换、地点列表和版本标识；
- 关闭后恢复原日期、滚动位置和已选地点；
- 仅在首次打开时动态加载 `AmapMap`；
- 没有地图条件时不渲染空地图，仅禁用按钮并说明原因。

### 5.3 顶栏

顶栏只保留全局信息和操作：

- 路书标题；
- 当前阶段名称；
- 保存/同步状态；
- 历史版本、撤销；
- 行程完成后的“生成最终页”。

详细进度不应仅放在顶栏，应在对话区和任务面板同时提供可见反馈。

## 6. 阶段状态模型

前后端统一使用稳定的业务阶段，不由组件自行拼接临时状态。

```ts
type PlanningPhase =
  | "understanding"
  | "clarifying"
  | "confirming_requirements"
  | "generating_recommendations"
  | "selecting_places"
  | "building_itinerary"
  | "itinerary_ready"
  | "editing"
  | "finalizing"
  | "failed";
```

### 6.1 阶段与界面映射

| 阶段 | 左侧对话区 | 右侧任务面板 | 主要用户操作 |
| --- | --- | --- | --- |
| `understanding` | 用户消息、AI 接收反馈 | 已识别条件骨架和解析状态 | 等待或补充 |
| `clarifying` | AI 问题、快捷回答 | 待确认条件和问题卡 | 选择、输入、跳过 |
| `confirming_requirements` | AI 确认说明 | 完整需求摘要 | 确认或逐项修改 |
| `generating_recommendations` | 推荐依据说明 | 搜索阶段和候选骨架 | 等待、取消 |
| `selecting_places` | 选择反馈 | 候选地点与取舍 | 接受、拒绝、替换 |
| `building_itinerary` | 编排说明 | 分日编排和验证进度 | 等待、取消 |
| `itinerary_ready` | 调整对话 | 完整分日行程 | 查看地图、修改、最终页 |
| `editing` | 修改指令和影响说明 | 提案预览 | 接受或拒绝 |
| `finalizing` | 最终生成反馈 | 固定版本生成进度 | 等待 |
| `failed` | 可理解错误 | 失败节点和可恢复操作 | 重试或调整 |

### 6.2 阶段来源优先级

阶段必须按以下顺序确定：

1. 服务端 Workflow Run 的当前阶段；
2. 未决中断或提案状态；
3. 当前快照是否已有完整行程；
4. 本地仅用于请求发出至服务端确认前的瞬时阶段。

禁止仅用 `days_plan.length`、`recommendations !== null` 等零散条件作为全局阶段真相。

## 7. 需求确认设计

### 7.1 字段状态

需求字段增加面向交互的决策状态：

```text
missing      尚未提供
suggested    系统建议，等待确认
confirmed    用户已确认
skipped      用户明确选择不考虑
conflicted   存在冲突或歧义
```

现有 `source` 继续保留，用于表示数据来源：

```text
explicit | inferred | default | missing
```

字段状态和字段来源不能合并为一个枚举。例如“系统建议的适中节奏”应为 `source=default`、`decision_status=suggested`。

### 7.2 新增需求字段

为支持目的地内部规划和模糊日期，建议新增：

```text
trip_scope:
- door_to_door
- destination_only

date_precision:
- exact
- range
- month_only
- flexible

date_range_start / date_range_end
travel_month
```

交通方式扩展为：

```text
driving
walking
public_transit
taxi
cycling
mixed
system_decides
```

路线服务可在规划阶段将 `mixed` 和 `system_decides` 解析为每一段的实际交通方式，而不是强迫整趟旅行只有一种方式。

### 7.3 澄清问题协议

`ClarificationQuestion` 扩展为：

```json
{
  "question_id": "clarify-trip-scope",
  "issue_code": "missing_trip_scope",
  "fields": ["trip_scope", "origin"],
  "prompt": "这次需要把出发地和往返交通也规划进去吗？",
  "input_type": "single_choice",
  "required": true,
  "options": [
    {
      "value": "destination_only",
      "label": "只规划北京市内",
      "description": "不考虑从其他城市到北京的往返交通"
    },
    {
      "value": "door_to_door",
      "label": "包含往返",
      "description": "下一步继续填写出发城市"
    }
  ],
  "allow_skip": false,
  "skip_label": null
}
```

`input_type` 一期支持：

- `single_choice`；
- `multi_choice`；
- `date`；
- `date_range`；
- `text`。

### 7.4 补问优先级

问题优先级从高到低为：

1. 规划范围：目的地、天数、是否包含往返；
2. 数据有效性：日期精度、节假日或营业时间依赖；
3. 路线结构：交通方式、同行人群、行动能力；
4. 硬约束：必去、排除、固定预约；
5. 个性偏好：主题、节奏、拥挤容忍度、远郊接受度。

每轮最多展示一个问题组，最多覆盖三个强相关字段。只有前一个答案会改变后续问题时，必须分轮询问。

### 7.5 阻断规则调整

- `trip_scope=destination_only` 时，`origin` 不再阻断；
- `date_precision=month_only` 或 `flexible` 时，缺少准确 `start_date` 不阻断基础推荐，但天气、营业时间和节假日结论标记为不可验证；
- 未选择交通方式时可使用 `system_decides` 进入建议确认，不应直接失败；
- 普通偏好可以采用系统建议，但必须在规划前摘要中展示；
- 用户明确选择“暂不确定”时记录为 `skipped` 或相应精度状态，不能继续按 `missing` 重复询问；
- 目的地和天数仍属于最小规划输入，除非用户只要求咨询而非生成路线。

## 8. 任务反馈与对话体验

### 8.1 乐观反馈

用户发送消息后立即执行：

1. 将用户消息以 `pending` 状态加入本地消息列表；
2. 清空输入框并保留失败恢复内容；
3. 插入 AI 工作状态，例如“收到，我先整理已知条件”；
4. 右侧切换到 `understanding`；
5. 请求成功后用服务端消息 ID 替换临时 ID；
6. 请求失败时将消息标记为失败并提供“重新发送”。

不能等待完整 `refresh()` 后才显示用户消息。

### 8.2 可见工作过程

允许展示：

- 当前执行步骤；
- 已识别和仍缺少的条件；
- 外部查询数量；
- 推荐和路线筛选结果数量；
- 需要用户确认的原因；
- 下一步动作和失败恢复建议。

不展示：

- 模型隐藏思维链；
- 内部 Prompt；
- 无法验证的主观推理流水账；
- 高频 token 级别的伪实时文本。

### 8.3 进度层级

进度分为三级：

- **阶段**：需求确认、地点推荐、路线编排；
- **步骤**：正在搜索景点、正在验证交通、正在检查日容量；
- **结果摘要**：找到 12 个候选、保留 8 个、3 个需要确认。

前端进度组件显示步骤列表或时间线，不能只显示百分比。对于无法精确估算的 LLM 和供应商请求，使用不确定进度状态，而不是虚构百分比。

### 8.4 可访问性

- 关键错误使用 `role="alert"`；
- 普通阶段完成使用集中式 `aria-live="polite"`；
- 高频步骤变化不逐条进入 live region；
- 快捷回答使用原生 `button`、`input`、`fieldset` 和 `legend`；
- 地图抽屉打开和关闭后正确管理焦点；
- 动画遵循 `prefers-reduced-motion`；
- 选中、成功、失败不能只依赖颜色表达。

## 9. 右侧任务面板

### 9.1 需求确认视图

包含：

- 当前阶段和说明；
- 已确认、待确认、系统建议、已跳过四组条件；
- 当前澄清问题；
- 快捷选项或输入控件；
- “继续规划”或“确认需求”操作。

回答可以在左侧消息气泡下方或右侧任务面板中出现。统一规则如下：

- 简单单选问题在左侧 AI 消息下方提供快捷按钮；
- 日期、多选、地点候选等需要比较空间的内容在右侧面板展示；
- 两处操作绑定同一个 question state，不能产生两套独立状态。

### 9.2 地点选择视图

候选卡片包含：

- 名称、类型、行政区和地址；
- 推荐理由；
- 与已选地点的交通取舍；
- 事实状态与来源；
- 接受、拒绝、替换操作；
- 拒绝原因快捷项。

顶部持续显示已选数量、建议范围和生成路线所需最小数量，但不得使用固定“至少接受 3 个”作为所有旅行的通用业务规则，应结合天数和强度计算。

### 9.3 路线生成视图

显示：

- 已完成的规划步骤；
- 当前正在处理的日期或约束；
- 路线验证、天气查询和冲突修复状态；
- 可恢复警告；
- 取消操作。

### 9.4 完整行程视图

只有 `itinerary_ready` 后展示：

- 日期标签和每日主题；
- 经过排序的地点列表；
- 相邻地点距离、耗时和交通方式；
- 天气、预警和备注；
- 冲突与降级事实状态；
- 查看地图、调整路线和生成最终页。

版本历史和提案预览属于次级信息，默认折叠或放入独立侧栏，避免持续挤占主任务空间。

## 10. 实时进度技术方案

### 10.1 工作流状态快照

扩展 `GET /api/workflow-runs/{run_id}`，返回：

```json
{
  "workflow_run_id": "...",
  "routebook_id": "...",
  "phase": "clarifying",
  "stage": "waiting_for_clarification",
  "status": "interrupted",
  "message": "还需要确认行程范围",
  "progress": {
    "completed": 2,
    "total": 4,
    "indeterminate": false
  },
  "latest_event_id": "...",
  "interrupt": {},
  "updated_at": "..."
}
```

该接口是当前状态真相，SSE 是增量通知通道。

### 10.2 事件持久化

一期可选择以下任一方案：

1. Redis Stream 保存短期事件，PostgreSQL 保存 Workflow Run 最新快照；
2. PostgreSQL `workflow_events` 保存完整事件，再通过 Redis 发送唤醒通知。

推荐方案 1：

- 事件写入 Redis Stream；
- 同一事务边界附近更新 Workflow Run 最新快照；
- SSE 根据事件 ID 读取和推送；
- 设置有限保留长度和过期时间；
- 长期审计信息仍保存在 PostgreSQL。

纯 Redis Pub/Sub 不再承担唯一进度来源。

### 10.3 SSE 恢复

- 客户端携带 `Last-Event-ID`；
- 服务端先回放遗漏事件，再进入实时等待；
- 无事件 ID 时先发送当前状态快照；
- 前端断线后显示非阻塞重连状态；
- 重连超时则调用工作流状态接口补偿；
- 页面重新加载后根据 RouteBook 当前活动 Run 恢复订阅。

### 10.4 异步化范围

以下操作统一进入 Workflow Run：

- 需求理解和补问；
- 地点推荐生成与替换；
- 路线编排和验证；
- 复杂局部修改；
- 最终页生成。

简单的接受、拒绝、切换日期等确定性操作仍可使用同步 API，但必须及时更新工作流或路书快照。

### 10.5 事件建议

```text
message.accepted
requirements.extracting
requirements.extracted
requirements.clarification_required
requirements.confirmed
recommendations.searching
recommendations.ranking
recommendations.ready
itinerary.clustering
itinerary.routing
itinerary.validating
itinerary.repairing
itinerary.ready
workflow.failed
workflow.completed
```

每个事件至少包含：

- `event_id`；
- `workflow_run_id`；
- `phase`；
- `stage`；
- `status`；
- 用户可见消息；
- 结构化结果摘要；
- 时间戳。

## 11. 前端改造方案

### 11.1 组件拆分

将当前大型工作区组件拆分为：

```text
RouteBookWorkspace
├── WorkspaceHeader
├── ConversationPanel
│   ├── MessageList
│   ├── AssistantActivity
│   ├── InlineQuickReplies
│   └── MessageComposer
├── PlanningPanel
│   ├── RequirementConfirmation
│   ├── RecommendationSelection
│   ├── ItineraryProgress
│   ├── ItineraryView
│   └── ProposalReview
├── MapDrawer
└── WorkflowAnnouncer
```

`RouteBookWorkspace` 只负责编排数据和阶段，不继续包含所有业务视图细节。

### 11.2 状态管理

至少拆分以下状态：

- `submissionState`：本地发送、失败、重试；
- `workflowState`：Run、phase、stage、status、progress；
- `conversationState`：消息与临时消息；
- `planningState`：需求、推荐、行程、提案；
- `viewState`：当前日期、地图开关、已选地点、历史版本。

用 `isSubmitting`、`isWorkflowRunning`、`isMutatingProposal` 等语义状态替换一个通用 `busy`。

### 11.3 数据获取

- 首次加载并行获取路书、消息、活动 Run 和当前规划产物；
- 活动 Run 优先建立 SSE；
- SSE 事件按影响范围更新局部状态；
- 只在阶段结束或发生版本变更时执行完整 refresh；
- 推荐与路线请求不能通过长时间同步 HTTP 阻塞 UI。

## 12. 后端改造方案

### 12.1 Requirement 模块

- 扩展需求字段和交通方式枚举；
- 增加字段决策状态；
- 扩展 ClarificationQuestion 结构；
- 将固定必填规则改为条件阻断规则；
- 增加问题优先级和每轮问题组策略；
- 记录跳过和系统代决策，避免重复询问。

### 12.2 Workflow 模块

- 为推荐、规划和最终生成建立统一 Workflow Run；
- 将大节点拆为可观测步骤；
- 每个步骤开始和完成时发布结构化事件；
- 工作流表保存最新 phase、stage、message 和 event ID；
- 提供活动 Run 查询和取消能力。

### 12.3 Progress 模块

- 从单纯 Pub/Sub 升级为可回放事件流；
- 支持 `Last-Event-ID`；
- SSE 首帧发送状态快照；
- 终态包含 `interrupted`；
- 统一终态关闭、重连和错误语义。

### 12.4 API 合同

需要更新并重新导出：

- `ClarificationQuestion`；
- `RequirementSnapshot`；
- `WorkflowRunRead`；
- `ProgressEvent`；
- 推荐和行程生成的 Accepted Response；
- 活动工作流、取消工作流接口；
- OpenAPI 和前端 TypeScript 类型。

## 13. 兼容与迁移

### 13.1 数据兼容

- 现有缺少 `trip_scope` 的快照按 `door_to_door` 解释，但首次进入编辑时提示确认；
- 现有 `start_date` 映射为 `date_precision=exact`；
- 现有 `driving/walking` 保持有效；
- 新字段使用可空迁移，并由领域服务逐步补齐；
- 旧消息中只有 `prompt` 的澄清问题继续按文本方式显示。

### 13.2 前端兼容

- 服务端未返回 `phase` 时，前端使用集中式兼容函数推导；
- 推导逻辑只用于迁移期，不散落在各组件；
- 地图入口只依赖快照数据，不依赖旧布局；
- 历史版本仍可只读查看行程和地图。

## 14. 实施计划

### 阶段 A：布局与即时反馈

目标：先解决地图占位和“发送后没反应”。

- 三栏改双栏；
- 地图改为按需打开；
- 拆分对话区和任务面板；
- 增加乐观消息和 AI 活动状态；
- 建立集中式 `PlanningPhase` 兼容推导；
- 增加自动滚动、错误重发和基础可访问性。

退出标准：用户发送消息后立即看到反馈，需求阶段不加载地图，现有流程功能不回退。

### 阶段 B：结构化需求确认

目标：支持真正的多轮确认和“不考虑出发地”。

- 扩展需求字段和澄清问题协议；
- 调整阻断规则；
- 实现问题卡、快捷回答和需求摘要；
- 支持目的地内部规划、日期精度和混合交通；
- 更新 Graph 中断和恢复测试。

退出标准：“9 月北京三日游”能够按上下文逐轮确认；选择目的地内部规划后不再追问出发地。

### 阶段 C：统一异步工作流与进度恢复

目标：推荐和规划全程可见、可恢复。

- 推荐和行程生成异步化；
- 扩展工作流状态接口；
- 进度迁移至可回放事件流；
- 支持断线恢复、刷新恢复和取消；
- 右侧加入路线生成时间线。

退出标准：任何耗时任务都有阶段反馈，刷新页面不丢失任务，断线后可恢复遗漏事件。

### 阶段 D：智能问题策略与体验优化

目标：减少无效追问，提高建议质量。

- 问题优先级和信息增益策略；
- 根据已知条件动态生成选项；
- 系统建议默认值及原因；
- 推荐和路线取舍说明；
- 移动端、键盘、读屏和性能专项验证。

退出标准：常见规划案例没有重复问题，普通偏好可授权系统处理，用户能理解每个关键取舍。

## 15. 测试方案

### 15.1 需求对话用例

至少覆盖：

1. “规划 9 月份北京三日游”；
2. 用户补充出发地后继续询问交通和偏好；
3. 用户选择不考虑出发地；
4. 只有月份，没有具体日期；
5. 用户说“日期暂时不确定”；
6. 公共交通、打车、自驾、混合交通；
7. 老人、儿童、行动不便同行；
8. 用户选择“你来安排”；
9. 用户修改已确认字段；
10. 歧义输入、矛盾输入和提取失败。

### 15.2 前端测试

- 初始工作台不渲染地图；
- 行程完成后地图按钮可用；
- 地图打开关闭保留日期和地点状态；
- 消息发送后立即显示 pending 消息；
- 请求失败可重发；
- 不同 phase 渲染正确任务面板；
- 快捷回答与文本回答进入同一恢复接口；
- 历史版本只读；
- 键盘可完成需求确认、地点选择和地图关闭。

### 15.3 实时链路测试

- 事件在前端订阅前发布仍能回放；
- SSE 断线后携带事件 ID 恢复；
- 页面刷新后恢复活动 Run；
- Worker 重试不重复提交版本；
- 中断状态能恢复且不会错误关闭；
- 推荐和规划失败能定位到具体步骤并重试。

### 15.4 性能测试

- 初始需求阶段不下载高德地图资源；
- 地图首次打开按需加载；
- 消息和阶段切换不引发全工作区重复布局；
- 长对话和长行程列表保持可操作；
- 动态区域没有明显布局跳动。

## 16. 验收标准

### 16.1 布局

- 需求、推荐和路线生成阶段默认只显示对话与任务面板；
- 地图不常驻，不在无路线时初始化；
- 完整行程形成后可通过明确入口查看地图；
- 桌面端、平板和移动端均能完成核心流程。

### 16.2 需求确认

- 系统可基于上下文进行多轮补问；
- 用户能通过选项或自然语言回答；
- 选择“不考虑出发地”后不再被重复询问；
- 已确认、建议、跳过和缺失状态清晰可见；
- 每轮问题数量和优先级符合本文规则。

### 16.3 任务反馈

- 用户提交后 100 毫秒内出现本地视觉反馈；
- 超过 1 秒的任务都有可见状态；
- 超过 3 秒的任务至少显示阶段和当前步骤；
- 错误包含原因、影响和可执行恢复操作；
- 不展示模型隐藏思维链。

### 16.4 右侧面板

- 右侧内容与服务端规划阶段一致；
- 需求确认完成前不展示空分日行程；
- 地点选择完成前不展示伪完整路线；
- `itinerary_ready` 后才展示完整路线信息和最终操作。

### 16.5 实时可靠性

- 页面刷新和 SSE 重连不丢失工作流状态；
- 早于订阅发布的进度可以恢复；
- 所有耗时生成操作均有统一 Run ID；
- 同一工作流重试不会重复创建正式版本。

## 17. 非目标

本轮暂不包含：

- 展示模型完整思维链；
- 多用户协同编辑；
- 跨路书长期用户画像；
- 全量公共交通换乘算法自研；
- 复杂 VRP 或多车路线优化；
- 将地图改造成独立 GIS 编辑器；
- 为了动画效果引入大型 UI 或状态库。

## 18. 风险与决策

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 新旧需求快照字段不一致 | 历史路书无法读取 | 可空迁移、集中兼容转换、历史用例回归 |
| 交通枚举扩展影响路线提供商 | 无法直接查询 mixed | 规划阶段拆分为具体路段方式 |
| 进度事件过多 | 前端噪音、存储膨胀 | 阶段事件持久化，高频内部日志不外发 |
| 双栏在小屏空间不足 | 交互拥挤 | 移动端单栏阶段切换，不强行并排 |
| AI 动态问题不稳定 | 重复或无关追问 | 规则排序优先，LLM 只负责文案和候选选项 |
| 同时运行多个 Run | UI 阶段冲突 | 每个路书标识一个前台活动 Run，其他进入历史或取消 |

本方案确认以下产品决策：

1. 地图是完成后按需打开的路线浏览工具，不是规划初期常驻面板；
2. 右侧是阶段任务面板，只有行程完成后才成为完整路线面板；
3. 需求确认采用规则控制的渐进式补问，不采用一次性大表单；
4. 用户可以明确跳过出发地和准确日期，但系统必须标明由此带来的事实限制；
5. 实时反馈展示工作步骤和可解释摘要，不展示隐藏思维链；
6. SSE 只负责增量传输，持久化工作流状态才是恢复依据。
