## 这个想法，来自一次青甘大环线规划

前段时间，我想规划一次青甘大环线旅行。

真正开始准备以后，我才发现，设计一条旅行路线远比“选几个想去的景点”麻烦。青甘大环线跨度很大，沿途有青海湖、茶卡盐湖、翡翠湖、敦煌、张掖等很多地方。哪些值得去、每天开多远、在哪里住宿、路线会不会折返，都需要一点点查。

我先在小红书上看别人的行程笔记，了解大家通常怎么安排天数、哪些地方容易踩坑；然后又去抖音看沿途的实景和自驾分享，判断一个地方到底值不值得专门绕过去；涉及具体路线时，还要打开高德地图，一个地点一个地点地搜索，查看距离和驾驶时间。

信息散落在不同平台里，我只能一边看，一边把有用的内容记下来。

很快，我的笔记里就堆满了景点名称、住宿地点、公里数、开放时间和各种提醒。资料看了不少，但真正把它们拼成一条路线时，又是另外一件事。

比如某一天安排得太满，就要删掉一个地点；删掉以后，住宿位置可能需要调整；路线换了，第二天的出发位置和驾驶时间也会跟着变化。一个看似很小的修改，经常要重新打开地图，把前后几天再算一遍。

我就在几个平台、地图和笔记之间来回切换，反复比较，最后才整理出一版自己觉得相对合理的旅行线路。

这件事耗费的精力比我预想得多。但也正是在这个过程中，我突然有了一个想法：

> 能不能把我查资料、筛选地点、安排日期、计算路线和反复调整的过程，提炼成一套可以复用的规划流程？

如果这套流程能够被复用，那么下一次规划旅行时，用户不需要从头翻很多攻略，也不用自己在多个工具之间反复搬运信息。只要从一个大概的想法开始，系统就可以逐步追问条件、查找资料、生成路线，再根据用户的反馈不断调整。

而每一次调整，都不应该只是重新生成一段攻略文字。它应该沉淀为一份真正的路书：知道每天去哪里、地点之间怎么走、预计花多久、哪些内容已经确认，以及这次修改影响了什么。

这就是 RouteBook Agent 最初的来源。

我想做的不是一个输入地点就吐出答案的旅行攻略生成器，而是一款能够承接完整规划过程的产品：把零散想法变成结构化行程，再通过持续沟通和调整，最终完成一条真正属于用户自己的旅行路线。

## 为什么是“路书”，而不只是“行程”

我给这个项目取名 RouteBook Agent。

“行程”很容易让人想到一张按日期排列的清单，但“路书”包含的东西更多：地点之间怎么走、每天走多远、预计花多久、天气怎么样、哪些内容已经确认、哪些信息还没有验证，以及这份计划经历过哪些修改。

我希望最终看到的不是一大段连续文字，而是几个彼此一致的视图：

- 对话里可以继续修改需求；
- 行程区按天展示安排；
- 地图上能看到地点和路线；
- 天气和风险与具体日期关联；
- 每次修改都能知道改了什么；
- 最终可以生成一份固定版本的路书页面。

这也带来了项目最重要的一条原则：

> 对话负责理解用户，但结构化路书才是当前结果的唯一事实。

如果地图、每日行程和聊天回复各自维护一套内容，这个产品迟早会乱。它们必须读取同一份路书版本。

## 第一次整理需求时，我几乎想把整个旅游攻略做进去

方向确定后，我开始列需求。

这一步很容易失控。旅行规划天然会牵扯大量信息：景点、营业时间、门票、预约、酒店、房价、火车、航班、天气、餐厅、停车、加油、充电、道路管制、预算和安全风险。

再加上 Agent 本身，我还想做需求补问、多个候选方案、版本比较、撤销、锁定、分享和导出。

第一版整体需求很快就变成了一份六百多行的文档。它并不是没有价值，至少让我看清了这个产品完整形态可能是什么样。但它不适合作为第一阶段的开发清单。

如果照着完整需求直接开工，我很可能花很长时间接各种数据源，最后连最核心的对话修改闭环都没有跑通。

所以我没有马上写代码，而是先把需求拆成了两层：

1. **整体产品需求**：记录未来完整的产品能力；
2. **一期功能需求**：只保留能够验证产品核心价值的最小闭环。

这两个文档解决的是不同问题。整体需求告诉我以后可能走到哪里，一期需求则明确现在必须做到哪里为止。

## 先做一期，实现最小MVP

我给一期定了一个很简单的目标：

> 用户从一句自然语言开始，最终得到一份可以保存、修改、在地图上展示的结构化路书。

围绕这个目标，我保留了下面这些能力：

1. 从对话中提取出发地、日期、天数、交通方式和目标地点；
2. 信息不足时，只补问会阻断规划的问题；
3. 搜索并确认地点，处理重名地点；
4. 生成按天组织的地点顺序；
5. 查询地点之间的路线、距离和预计耗时；
6. 获取每日主要停留地的天气和灾害预警；
7. 在地图上展示地点和分日路线；
8. 支持增加、删除、替换地点，以及只修改某一天；
9. 重要修改先预览，用户确认后再写入正式版本；
10. 保存每次修改产生的版本，并支持撤销最近一次修改；
11. 最终生成绑定明确版本的 HTML 路书页面。

对应地，我也明确砍掉了一批看起来很有吸引力的功能：

- 火车、航班实时班次和余票；
- 酒店搜索、房态和实时价格；
- 景点门票、预约和实时客流；
- 餐厅营业状态；
- 充电桩和加油站实时可用性；
- 精确预算；
- 实时导航和临时道路管制；
- 自动下单、支付和多人协作。

砍掉它们不是因为这些能力不重要，而是因为它们不能帮助我更快验证最核心的问题：用户能不能通过多轮对话，稳定地维护一份可视化路书。

还有一个更现实的原因——数据。

## 数据源调查，是需求收缩的真正转折点

一开始我也想过，既然要做旅行规划，最好把酒店、班次、票价和景区预约全部查出来。

真正开始调查后，我发现“网页上能查到”和“产品里有稳定接口可用”完全是两回事。

12306、航班、酒店和景区预约往往涉及登录、验证码、反自动化、商业授权和频繁变化的页面结构。即使短期能通过某些非公开接口拿到数据，也很难把它当成一个长期可靠的产品依赖。

而且这类数据有很强的时效性。一次调用成功不代表半小时后仍然有效。如果系统没有保存查询时间、有效期和验证状态，就很容易把过期信息当成事实展示给用户。

因此我给外部数据加了一条准入规则：

> 没有稳定正式接口、无法说明来源和时效的数据，不进入一期自动规划。

经过这一轮筛选，一期最终只留下两个正式外部数据源：高德地图和和风天气。

高德负责地点检索、地理编码、驾车与步行路线、距离和预计耗时；和风天气负责逐日预报、逐小时预报和灾害预警。

其他信息不是完全不能出现。用户依然可以手工记录已订酒店、已购车票、景点预约码和注意事项，但这些内容只作为用户备注保存，系统不会把它们伪装成已经验证的事实。

这个取舍让一期范围一下子清楚了很多。

## 在技术选型之前，我先用真实接口跑了一遍

我不想只看文档就开始设计适配器，所以先拿真实 Key 做了一轮接口验证。

测试地点选了武汉黄鹤楼。

高德的地理编码成功返回了标准地址和坐标；POI 搜索返回了 10 个候选；驾车路径接口返回了两条路线，其中首选路线包含距离、预计时长、过路费和红绿灯数量。

这次验证也暴露了一个产品问题：地点搜索有结果，不代表可以直接采用第一条。重名地点、多入口景区和同名商户都可能产生多个候选，所以“地点消歧”必须成为正式流程，而不是接口层的一个小细节。

和风天气的三日预报、24 小时预报和灾害预警也都调用成功。测试时刚好返回了一条武汉高温黄色预警。

有了真实接口和数据，开始执行这件事心里也有了底。

## Agent 在这个产品里到底负责什么

确定一期功能后，接下来最大的技术问题是：哪些事情交给模型，哪些事情必须由普通代码完成？

如果把整个流程都交给模型，开发速度看起来会很快。模型可以理解需求、安排地点、生成路线说明，甚至直接输出一整份 JSON。

但这样做有一个根本问题：模型输出是不稳定的，而路书的版本、地点坐标、路线距离和确认状态必须稳定。

所以我给 LLM 划定了很窄但很重要的职责：

- 从自然语言提取结构化需求；
- 识别用户是在创建、修改、确认、撤销还是生成最终版；
- 解析“第二天”“这个地方”“刚才那个方案”等上下文引用；
- 信息不明确时生成少量补问；
- 生成修改摘要和天气风险说明。

模型不能做的事情更多：

- 不能自己编造坐标、距离、耗时和天气；
- 不能绕过确认规则；
- 不能直接修改数据库；
- 不能自己生成版本号；
- 不能把未经接口验证的信息标记为可信事实。

模型负责理解语言，供应商接口负责提供外部事实，领域服务负责执行业务规则。

这三个边界确定之后，Agent 才不是一个“会聊天的黑盒”，而是整个系统里一个可控的参与者。

## 为什么最后选择了 LangGraph

路书的流程并不是一次请求、一次返回。

地点可能存在多个候选，需要暂停等待用户选择；重要修改也必须先生成预览，等用户确认后才能继续。外部接口可能失败，任务需要恢复；用户也可能在流程暂停期间继续修改当前路书。

我需要的不只是按顺序调用几个函数，而是一个能表达暂停、恢复、分支和子流程的编排层。

因此一期选择 LangGraph 来组织 Agent 流程。

主流程大致分成几条子图：

- 需求提取；
- 地点解析与消歧；
- 初稿生成；
- 局部修改；
- 提案确认；
- 撤销；
- 最终版本生成。

例如初稿生成流程会先加载已经确认的需求，再分配每日地点，优化地点顺序，然后并行查询路线、天气和预警，最后执行完整性检查并提交第一个版本。

局部修改流程则先解析用户意图，计算影响范围，生成预览，判断是否需要确认，再只重新计算受影响的日期、路线段和天气位置。

这里有一个非常关键的边界：

> LangGraph 保存的是流程状态，不是路书的正式版本。

Graph 可以暂停在“等待用户确认”，但用户当前已经确认的路书仍然应该正常存在。不能因为工作流暂停，就让整个业务对象也变成半成品。

## 我为“反复修改路线”设计了什么

这个项目里，路线不会是一次性完整生成的，而是不断调整改善的。

用户说“第二天太赶了，换一条轻松点的路线”时，系统需要先知道：受影响的是哪一天、哪些地点、哪些路线段，以及天气查询位置是否发生变化。

技术方案里，我让影响计算至少产生下面这些内容：

```json
{
  "affected_days": [2],
  "affected_place_ids": ["place_4", "place_7"],
  "affected_segment_ids": ["segment_3", "segment_4"],
  "weather_locations_changed": true,
  "major_route_changed": false,
  "requires_confirmation": false
}
```

系统只重新计算这些受影响对象。

提交之前，还会比较其他日期的规范化哈希。如果用户只修改第二天，但第三天的数据也发生了变化，系统会拒绝提交，并记录一次非预期范围变更。

这可能比“让模型重新生成整份行程”麻烦得多，但它直接决定了这个产品是否值得信任。

## 为什么路书版本必须不可变

只要支持确认、预览和撤销，就绕不开版本设计。

我最终选择在 PostgreSQL 中保存不可变的路书快照。每次用户确认一个有效修改，就创建一个新版本，而不是覆盖旧记录。

每个版本至少包含：

- 已确认需求；
- 地点；
- 每日行程；
- 路线段；
- 天气；
- 用户备注；
- 风险提示；
- 修改摘要和触发它的用户表达。

待确认提案与正式版本分开保存。用户可以预览提案，但在点击确认之前，当前正式路书不会改变。

撤销也不是删除一个版本或把版本号减一，而是读取上一个版本的快照，再创建一个类型为 `undo` 的新版本。这样所有操作都有记录，也不会破坏历史。

最终分享页面同样绑定一个明确的版本 ID，而不是每次打开时读取“当前草稿”。否则用户分享出去的内容会随着后续修改悄悄变化。

## 一期为什么用了看起来并不“最小”的技术栈

一期技术方案最终定为：

- Next.js、React 和 TypeScript 负责页面；
- FastAPI 负责应用服务和接口；
- LangGraph 负责编排流程；
- PostgreSQL 保存业务数据、版本和工作流检查点；
- Redis 负责外部数据缓存、幂等键和进度事件；
- Celery 执行耗时工作流；
- SSE 向前端推送规划进度；
- Pydantic 校验模型输出和领域数据；
- 高德地图与和风天气提供外部事实。

乍看之下，这套技术栈对一个一期项目并不算轻。

但我没有选择微服务，而是先做模块化单体。Web、API 和 Worker 虽然是不同进程，业务代码仍然按照一个应用维护。这样既能保留流程恢复、异步执行和数据一致性，又不用在第一阶段承担分布式系统的额外成本。

Celery 和 Redis 也不是为了显得架构完整。路线和天气查询可能持续数秒，流程中还会出现暂停确认。如果这些任务全部放在一次 HTTP 请求里，连接中断和重试会变得很难处理。

FastAPI 接到消息后创建 Workflow Run，Celery Worker 启动或恢复 LangGraph，执行阶段通过 Redis 发布，再由 SSE 推给页面。用户能够看到“正在解析地点”“正在查询路线”“正在获取天气”，而不是盯着一个没有反馈的加载动画。

## 路线规划没有一开始就上复杂算法

另一个容易过度设计的地方是路线优化。

一期只处理 1～7 天、3～15 个主要地点，没有必要马上引入完整的车辆路径规划求解器。

我采用的是一套可解释的启发式方法：

1. 先按城市和行政区对地点分组；
2. 根据天数和行程强度分配地点；
3. 优先保证必去地点；
4. 用坐标直线距离生成初始顺序；
5. 使用最近邻得到每日初始路线；
6. 用有限次 2-opt 减少明显折返；
7. 最后再调用高德查询正式路线、距离和耗时。

直线距离只参与内部排序，不会作为正式距离展示。用户看到的路线数据仍然来自地图接口。

这套方案不一定能找到数学意义上的最优解，但它足够透明，也足够支撑一期验证。等以后地点规模和约束数量真的增加，再考虑更复杂的求解器。

## 第一阶段结束时，我真正得到的是什么

到这里，项目还没有进入大规模功能开发，但最重要的几个问题已经有了答案：

- 这个产品不是一次性的攻略生成器，而是持续维护路书的 Agent；
- 对话不是业务事实，结构化路书版本才是；
- 一期只验证地点、路线、天气、地图和局部修改闭环；
- 没有稳定数据接口的能力暂时不做；
- 模型负责理解，领域服务负责规则，供应商负责事实；
- LangGraph 负责暂停和恢复，但不保存正式业务版本；
- 每次确认修改都生成不可变版本；
- 外部接口失败可以降级，但不能伪造结果；
- 先用简单、可解释的路线算法跑通，再决定是否升级。

回头看，这个阶段最大的收获不是选出了多少技术，而是知道哪些东西现在不该做。

从 0 到 1 做项目时，列功能其实不难。真正难的是为每个功能找到存在的理由，再为每个暂时不做的功能找到足够坚定的边界。
