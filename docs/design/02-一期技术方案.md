## 1. 文档目的

本文给出路书 Agent 一期的整体技术方案，重点规定：

- 前后端、流程编排、数据库、缓存和异步任务的技术选型；
- LangGraph 与领域服务、业务数据之间的职责边界；
- 路书版本、修改提案、暂停确认和最终页面的数据一致性方案；
- 地点解析、行程生成、局部修改和最终生成的流程设计；
- 外部接口失败、任务恢复、并发修改和版本冲突的处理方式；
- 一期建议的工程结构、测试策略和实施顺序。

本文不替代功能需求和第三方接口规范。发生冲突时，以一期功能需求为最高优先级。

## 2. 方案摘要

一期采用以下总体方案：

> Next.js 负责交互和展示，FastAPI 提供应用服务，LangGraph 负责编排可暂停和可恢复的业务流程，领域服务负责确定性业务规则，PostgreSQL 不可变版本快照保存路书正式事实，Redis 和 Celery 负责缓存、进度和可靠异步执行。

核心设计原则：

1. **模型负责理解，不负责保存业务真相。**
2. **LangGraph 负责编排，不充当路书版本库。**
3. **业务规则由确定性领域服务执行。**
4. **每个已确认版本不可变，所有页面读取明确版本。**
5. **提案预览与正式版本隔离，确认后才生成新版本。**
6. **局部修改只重新计算最小影响范围。**
7. **外部事实必须来自供应商适配器，不允许模型虚构。**
8. **所有可恢复节点和外部副作用必须具备幂等性。**

## 3. 技术选型

| 层级 | 推荐技术 | 主要用途 |
| --- | --- | --- |
| Web 前端 | Next.js、React、TypeScript | 对话、行程、地图和最终页面 |
| UI | Tailwind CSS、shadcn/ui | 一期三栏布局和通用组件 |
| 地图 | 高德地图 JavaScript API | 地点标记、分日路线和地图联动 |
| 应用服务 | Python、FastAPI | REST API、SSE、业务服务和鉴权边界 |
| 流程编排 | LangGraph Python | 流程路由、暂停确认、恢复和节点状态 |
| 数据校验 | Pydantic | API、LLM 输出、Graph State 和领域 DTO 校验 |
| 数据访问 | SQLAlchemy 2、Alembic | ORM、事务和数据库迁移 |
| 主数据库 | PostgreSQL | 路书、不可变版本、提案、消息和运行记录 |
| Graph Checkpointer | LangGraph PostgreSQL Checkpointer | Graph 执行状态持久化 |
| 缓存 | Redis | 外部查询缓存、幂等键和进度事件 |
| 异步执行 | Celery | 可靠执行耗时 Graph 工作流 |
| LLM 接入 | OpenAI Responses API | 结构化需求提取、意图解析和文案生成 |
| 实时进度 | Server-Sent Events | 向前端推送生成阶段和结果更新 |
| 测试 | Pytest、Vitest、Playwright | 单元、集成、前端和端到端测试 |
| 本地环境 | Docker Compose | 统一启动 Web、API、Worker、PostgreSQL 和 Redis |

一期使用模块化单体，不拆分微服务。模块化单体可以减少分布式事务和部署复杂度，同时保留后续按领域拆分的边界。

### 4.1 部署单元

一期建议包含以下进程：

- `web`：Next.js；
- `api`：FastAPI；
- `worker`：Celery Worker，执行 LangGraph；
- `postgres`：业务数据库及 LangGraph checkpoint；
- `redis`：缓存、任务代理和进度事件。

PostgreSQL 可使用同一实例，但业务表和 LangGraph checkpoint 表应在逻辑上分离，建议使用不同 schema。

## 5. 职责边界

### 5.1 LangGraph

LangGraph 负责：

- 根据当前意图和业务状态选择下一节点；
- 编排需求提取、地点解析、路线生成、天气查询等步骤；
- 在地点消歧和重要修改确认处暂停；
- 恢复被暂停或失败的流程；
- 编排可并行的路线、天气和预警查询；
- 记录流程执行阶段并向前端发布进度；
- 聚合节点的结构化结果和错误。

LangGraph 不负责：

- 直接定义路书版本规则；
- 将 checkpoint 作为路书正式版本；
- 绕过领域服务直接覆盖当前版本；
- 根据模型输出直接生成正式坐标、路线或天气事实。

### 5.2 领域服务

领域服务负责：

- RouteBook 状态迁移；
- 需求字段合并和阻断项判断；
- 必去、排除、日期连续性等规则；
- 修改影响范围计算；
- 重要修改确认判定；
- 提案预览生成；
- 不可变版本创建和当前版本切换；
- 撤销和最终版本绑定；
- 提交前完整性校验和并发冲突检查。

### 5.3 LLM

LLM 负责：

- 从自然语言提取结构化需求变更；
- 识别创建、修改、确认、撤销和最终生成意图；
- 解析“第二天”“这个地点”等上下文引用；
- 在无法唯一解析时生成少量关键补问；
- 生成修改摘要、风险说明和天气建议文案。

LLM 不得：

- 自行产生正式坐标、距离、耗时或天气；
- 自行决定是否绕过用户确认；
- 自行生成或修改业务版本号；
- 将未经适配器验证的内容标记为 `verified`；
- 直接执行数据库写入。

## 6. LangGraph 流程设计

### 6.1 主图

`RouteBookGraph` 是统一入口，根据用户意图和路书状态路由到不同子图。

```text
接收用户消息
    ↓
加载路书上下文
    ↓
识别用户意图
    ├── 新建或补充需求 ──→ RequirementSubgraph
    ├── 地点确认       ──→ PlaceResolutionSubgraph
    ├── 生成初稿       ──→ InitialPlanningSubgraph
    ├── 修改行程       ──→ EditSubgraph
    ├── 确认或拒绝提案 ──→ 恢复对应 Workflow Run
    ├── 撤销           ──→ Undo Domain Service
    └── 生成最终版     ──→ FinalizeSubgraph
```

### 6.2 需求提取子图

```text
extract_requirement_patch
→ validate_llm_output
→ merge_requirements
→ derive_safe_defaults
→ validate_minimum_input
    ├── 信息不足 → build_clarification → interrupt
    ├── 存在用户地点 → route_to_place_resolution
    └── 需要系统推荐 → route_to_recommendation
```

主要输出：

- 本轮字段增量；
- 字段来源：用户明确、默认值、系统推断或待确认；
- 已确认需求摘要；
- 最多 1～3 个阻断问题。

需求提取和景点推荐必须是两个独立模型任务。`extract_requirement_patch` 只识别本轮用户明确表达的需求变化，不得填充推荐景点。

一期需求状态至少包含出发地、目的地、日期、天数、交通方式、同行人群、主题偏好、每日强度、拥挤容忍度、远郊接受度、必去、可选、排除和已去过地点。每个可从对话修改的字段保留 `value`、`source` 和 `confidence`，其中 `source` 取值为 `explicit | inferred | default | missing`。

推断值不得覆盖已确认值，也不得当作硬约束。补问只面向会阻断当前规划的信息；普通偏好缺失时使用明示默认值。

### 6.3 地点推荐子图

用户没有提供足够景点，或明确要求推荐时，进入 `RecommendationSubgraph`：

```text
build_recommendation_strategy
→ generate_search_tasks
→ recall_place_candidates
→ normalize_candidates
→ hard_filter_candidates
→ score_preference_match
→ select_diverse_recommendations
→ persist_proposed_places
    ├── 存在方向性歧义 → confirm_recommendation_direction → interrupt
    └── 无阻断歧义 → route_to_place_resolution
```

`build_recommendation_strategy` 只输出目标 POI 类型、主题权重、地理范围、最大交通成本、负面类型和多样性约束，不直接将模型记忆中的景点作为已验证地点。

推荐地点一律以 `proposed` 状态进入候选集，保存推荐理由、取舍、命中偏好和数据来源。用户拒绝时保存本路书内的 `too_far | too_crowded | not_interested | already_visited` 等理由，并重新排序。一期不将反馈存为跨路书长期画像。

### 6.4 地点解析子图

```text
search_places
→ normalize_candidates
→ classify_candidate_semantics
→ hard_filter_candidates
→ score_candidates
→ evaluate_resolution_policy
    ├── 高置信且无语义歧义 → persist_confirmed_places
    ├── 多个合理候选         → create_place_choices → interrupt
    ├── 用户表达为泛指概念   → create_preference_choices → interrupt
    └── 无有效结果             → retry_or_clarify → interrupt
```

只有用户确认或满足自动采用规则的地点，才能进入正式规划。

候选必须先执行确定性硬过滤，再执行打分。解析景区主体时，交通设施、公交或地铁站、直通车、旅行社、停车场和票务服务不得进入景区主体候选。入口、出口和游客中心可作为 `access_point` 保存，但不得替代景区主体。

候选基础分数由领域服务按名称、POI 类别、城市与行政区、地理范围、用户偏好和数据完整性计算，并对风险类别和风险名称扣分。权重和阈值必须可配置，并由评测集校准。

初始自动采用策略建议同时满足：`top1_score >= 0.85`、`top1_score - top2_score >= 0.15`、类别与行政区符合、未命中高风险信号，且用户表达不是“长城”“古镇”等泛指概念。“只有一个候选”、“名称包含关键词”或“名称完全相同”都不能单独作为自动采用依据。

LLM 可以辅助生成 `semantic_type`、拒绝理由和消歧文案，但硬过滤、阈值判定和最终状态迁移由领域服务执行。

### 6.5 初稿生成子图

```text
load_confirmed_requirements
→ arrange_days
→ optimize_place_order
→ fetch_route_segments ─┐
                        ├→ assemble_draft
→ fetch_weather ────────┤
→ fetch_warnings ───────┘
→ validate_draft
→ commit_initial_version
```

路线、天气和预警在依赖满足后并行查询。天气失败不阻断初稿生成，路线失败保留地点并生成明确的未验证路线段。

初稿规划应在 `optimize_place_order` 与 `assemble_draft` 之间增加 `validate_feasibility`。不可行时进入 `repair_itinerary` 并回到顺序优化，形成“生成—验证—修复”闭环。修复次数必须有上限，建议一期最多 3 次。

可自动修复调换日期、调整日内顺序、移除低优先级 `proposed` 地点或将远郊地点独立成日；不得删除 `must_visit` 或加入 `excluded` 地点。若必去约束、每日交通上限和天数无法同时满足，必须返回结构化冲突并中断请用户选择，不得伪造路线时长来消除冲突。

### 6.6 局部修改子图

```text
parse_edit_intent
→ resolve_references
→ calculate_impact
→ build_preview
→ evaluate_confirmation_requirement
    ├── 需要确认 → persist_proposal → interrupt
    └── 无需确认 → recompute_affected_scope
→ recompute_affected_scope
→ validate_unchanged_days
→ commit_new_version
```

`calculate_impact` 至少输出：

```json
{
  "affected_days": [2],
  "affected_place_ids": ["place_4", "place_7"],
  "affected_segment_ids": ["segment_3", "segment_4"],
  "weather_locations_changed": true,
  "major_route_changed": false,
  "requires_confirmation": false
}
```

提交前应比较未受影响日期的规范化哈希。若未受影响日期发生变化，拒绝提交并记录 `UNEXPECTED_SCOPE_CHANGE`。

### 6.7 最终生成子图

```text
load_target_version
→ validate_final_version
    ├── 存在阻断问题 → mark_blocked → return_issues
    └── 检查通过     → create_final_record
→ render_final_page
→ mark_final
```

最终页面必须绑定明确的 `routebook_version_id`，不得在访问时读取当前草稿版本。

## 7. Graph State 与业务状态

### 7.1 Graph State

Graph State 只保存一次工作流运行所需的短期上下文。

```python
class RouteBookGraphState(TypedDict):
    workflow_run_id: str
    routebook_id: str
    base_version_id: str | None
    user_message_id: str

    intent: dict | None
    requirement_patch: dict | None
    resolved_references: dict | None

    candidate_places: list[dict]
    confirmed_place_ids: list[str]

    affected_days: list[int]
    proposal_id: str | None

    job_stage: str
    warnings: list[dict]
    errors: list[dict]

    result_version_id: str | None
```

Graph State 不长期保存完整路书。节点通过 `base_version_id` 加载正式快照，提交成功后只保存 `result_version_id`。

### 7.2 双层状态

系统同时维护业务状态和流程状态。

业务状态：

```text
draft | planning | pending_confirmation | editable | blocked | final
```

流程状态：

```text
queued | running | interrupted | completed | failed | cancelled
```

两者不得直接等同。例如，Graph 可以处于 `interrupted`，RouteBook 处于 `pending_confirmation`，而当前正式版本仍然是上一个可编辑版本。

### 7.3 Thread ID

每次独立业务工作流使用新的 `thread_id`：

```text
thread_id = workflow_run_id
```

示例：

```text
routebook:rb_123:create:run_001
routebook:rb_123:edit:run_002
routebook:rb_123:finalize:run_003
```

不建议将 `routebook_id` 永久作为唯一 `thread_id`，避免不同提案、刷新任务和最终生成流程互相污染状态。

## 8. 暂停、恢复与幂等性

### 8.1 暂停场景

一期主要有两类暂停：

1. 地点存在多个候选或无法定位；
2. 删除必去地点、改变总天数、修改多日或改变主要路线。

暂停前应先把候选或提案写入业务表，再通过 `interrupt()` 返回可序列化的摘要。

### 8.2 节点拆分规则

推荐结构：

```text
纯计算节点 → 持久化提案节点 → interrupt 节点 → 正式提交节点
```

禁止在同一节点内先创建正式版本再执行 `interrupt()`。

LangGraph 恢复时可能重新执行节点，因此：

- 外部查询使用确定的缓存键；
- 提案创建使用幂等键或唯一约束；
- 版本创建必须检查 `workflow_run_id` 是否已提交；
- 消息写入使用客户端消息 ID 去重；
- Celery 任务允许安全重投；
- 正式提交集中在单独节点和单个数据库事务中。

### 9.2 `routebook_versions`

| 字段 | 说明 |
| --- | --- |
| `id` | 版本 ID |
| `routebook_id` | 所属路书 |
| `version_number` | 递增版本号 |

`snapshot_jsonb` 至少包含：

- requirements；
- places；
- days_plan；
- route_segments；
- weather；
- notes；

关系表用于检索、状态和约束，JSONB 快照用于保证一个版本能够独立、完整地渲染。版本创建后不得修改其快照。

### 9.4 `workflow_runs`

| 字段 | 说明 |
| --- | --- |

| `routebook_id` | 路书 ID |

| `base_version_id` | 启动时的基础版本 |

### 9.5 其他主要表

- `conversation_messages`：保存用户和系统消息；

- LangGraph checkpoint 表：由 checkpointer 管理，不作为业务表直接修改。

## 10. 版本与事务

### 10.1 创建新版本

所有确认后的有效修改使用以下事务：

1. 锁定或条件更新目标 RouteBook；
2. 检查当前版本等于 Workflow Run 的 `base_version_id`；
3. 执行领域完整性校验；
4. 插入新的不可变版本；
5. 更新 `routebooks.current_version_id`；
6. 更新业务状态；
7. 将提案标记为已处理；
8. 提交事务。

### 10.2 乐观并发控制

工作流可能暂停较长时间，因此提交时必须检查基础版本：

```sql
UPDATE routebooks
SET current_version_id = :new_version_id,
    updated_at = now()
WHERE id = :routebook_id
  AND current_version_id = :base_version_id;
```

更新行数为零时返回 `VERSION_CONFLICT`，不得覆盖其他流程已提交的修改。

### 10.3 撤销

撤销不删除历史版本，而是：

1. 找到当前版本的父版本；
2. 复制父版本快照；
3. 创建新的递增版本；
4. 将修改类型记录为 `undo`；
5. 将当前版本指向新版本。

## 11. 路线规划策略

一期采用可解释的启发式规划，不引入复杂 VRP 求解器。

1. 按城市和行政区对地点粗分组；
2. 根据天数和每日强度分配地点；
3. 优先保证必去地点；
4. 使用 GCJ-02 经纬度近似距离生成初始顺序；
5. 使用最近邻算法生成每日初始路线；
6. 使用有限次 2-opt 减少明显折返；
7. 对最终相邻地点调用高德路径规划；
8. 采用供应商首选路线；
9. 路线失败时保留地点并标记未验证。

直线距离只用于内部排序，不作为正式距离和耗时向用户展示。

建议的每日主要地点数量：

| 强度 | 每日主要地点数 | 规划倾向 |
| --- | --- | --- |
| 轻松 | 1～2 | 减少移动，增加停留 |
| 适中 | 2～3 | 默认策略 |
| 紧凑 | 3～4 | 接受更多移动 |

### 11.1 可行性约束与修复

每个行程日应生成可计算的 `DailyCapacity`，至少包含主要地点上限、活动总时长上限、交通总时长上限和单段交通时长上限。默认值由强度模板产生，用户明确约束优先。

`validate_feasibility` 至少检查：

- 必去地点是否全部进入行程；
- 排除和已拒绝地点是否误入；
- 所有正式地点是否具有经验证的 POI ID 和坐标；
- 同日地点是否跨区过远或出现明显折返；
- 每日活动和交通时长是否超过容量；
- 远郊景点是否与市区景点不合理混排；
- 景点类型是否过度重复；
- 相邻地点是否具有已验证路线或明确的未验证状态。

直线距离只能用于召回、分组和初排。可行性结论中的正式交通距离和时长必须来自高德路径规划结果。

## 12. LLM 接入设计

### 12.1 结构化输出

LLM 必须通过 JSON Schema 或等效严格结构输出以下对象：

- `RequirementPatch`；
- `UserIntent`；
- `EditIntent`；
- `ReferenceResolution`；
- `ClarificationQuestions`；
- `ChangeSummary`；
- `WeatherRiskSuggestion`；
- `RecommendationStrategy`；
- `PoiSemanticEvaluation`；
- `ItineraryProposal`；
- `ConstraintViolation`。

示例：

```json
{
  "intent": "replace_place",
  "target_day": 2,
  "target_place_ref": "黄鹤楼",
  "new_place_text": "湖北省博物馆",
  "confidence": 0.94,
  "requires_clarification": false
}
```

模型输出必须先通过 Pydantic 校验，再进入领域服务。校验失败时允许有限次数修复或降级为澄清问题。

### 12.2 Prompt 职责分离

一期不使用一个 Prompt 同时完成需求提取、景点推荐、POI 确认和行程编排。至少分为以下职责：

| Prompt | 只允许处理 | 明确禁止 |
| --- | --- | --- |
| `requirement_extraction` | 提取本轮需求增量、来源和歧义 | 推荐景点、生成路线 |
| `recommendation_strategy` | 生成检索策略、偏好权重和取舍 | 伪造 POI 事实或坐标 |
| `poi_semantic_evaluation` | 辅助区分景区主体、入口、交通和商户 | 绕过硬过滤或自行确认 |
| `itinerary_proposal` | 基于已验证输入给出排序建议和取舍 | 估算或编造距离、时长和开放信息 |
| `clarification` | 将阻断项压缩为 1～3 个问题 | 询问不影响当前规划的全部可选字段 |

所有 Prompt 必须将“用户明确信息”、“已确认业务状态”、“供应商事实”和“模型建议”作为不同输入分区，禁止将模型建议标记为 `verified`。

### 12.3 模型配置

- 模型名称通过环境变量配置，不写死在业务代码中；
- 一期优先选择支持 Structured Outputs 的低延迟模型；
- 复杂引用解析可配置升级模型；
- 生产环境固定模型快照；
- 模型升级前运行需求提取和修改意图评测集；
- 记录模型名、提示词版本、响应 ID、耗时和 token 使用量；
- 不将供应商会话状态作为路书长期数据源。

### 12.4 提示词版本

提示词应纳入代码版本管理，每类任务独立维护：

```text
prompts/
├── requirements/
├── intent/
├── reference_resolution/
├── change_summary/
└── weather_risk/
```

每次 LLM 调用记录 `prompt_version`，便于回归和审计。

## 13. 外部供应商与缓存

高德和和风天气的接口、字段映射、错误处理和凭证规则以 `01-第三方接口接入规范.md` 为准。

建议缓存键：

```text
poi:{provider}:{region}:{normalized_keyword}
geocode:{provider}:{region}:{normalized_address}
route:{provider}:{mode}:{origin_place_id}:{destination_place_id}:{params_hash}
weather:{provider}:{place_id}:{forecast_date}
warning:{provider}:{place_id}
```

缓存值保存规范化结果，不将第三方原始响应直接写入业务版本。

每次外部请求记录：

- provider 和 operation；
- request ID；
- Workflow Run ID；
- 耗时、HTTP 状态和内部错误码；
- 是否命中缓存和重试次数；
- 脱敏后的诊断信息。

日志不得包含 API Key、认证头、带 Key 的完整 URL或用户精确敏感地址。

## 14. 异步任务与实时进度

### 14.1 执行方式

FastAPI 接收到需要耗时处理的请求后：

1. 创建 `workflow_runs` 记录；
2. 将 Celery 任务入队；
3. Worker 创建或恢复 LangGraph；
4. 每个阶段更新 `workflow_runs.current_stage`；
5. 通过 Redis 发布进度事件；
6. FastAPI SSE 端点向浏览器转发事件；
7. Graph 完成后返回新版本 ID 或待确认提案。

### 14.2 阶段枚举

```text
queued
extracting_requirements
waiting_for_clarification
resolving_places
waiting_for_place_confirmation
planning_days
fetching_routes
fetching_weather
validating
waiting_for_change_confirmation
saving_version
rendering_final_page
completed
failed
```

### 14.3 SSE 事件

建议统一格式：

```json
{
  "event_id": "evt_123",
  "workflow_run_id": "run_001",
  "routebook_id": "rb_123",
  "stage": "fetching_routes",
  "status": "running",
  "message": "正在查询第 2 天路线",
  "progress": {
    "completed": 3,
    "total": 5
  },
  "occurred_at": "2026-08-07T15:00:00+08:00"
}
```

客户端断线重连后，应先从 REST API 获取 Workflow Run 当前状态，再继续订阅新事件。

## 16. 前端设计

一期页面保持需求规定的单页面布局：

- 顶部：标题、日期、天数、交通方式、业务状态和版本；
- 左侧：对话历史、候选选择、确认操作和输入框；
- 中间：需求摘要、每日行程、修改提示和提案预览；
- 右侧：高德地图、地点标记和分日路线；
- 提示区：天气预警、路线失败、过期数据和未验证信息。

前端状态按版本绑定：

```text
routebook_id + displayed_version_id + proposal_id?
```

地图、行程和天气必须从同一个版本响应中派生，避免各区域独立请求不同版本的数据。

提案预览使用独立视觉状态，不修改正式版本对象。确认成功后，前端统一切换到服务端返回的新版本 ID。

## 17. 最终页面

最终页面生成流程：

1. 指定目标 `routebook_version_id`；
2. 执行最终完整性检查；
3. 创建不可变 `final_pages` 记录；
4. 根据隐私规则生成分享视图；
5. Next.js 服务端渲染固定布局；
6. 分享页面始终读取绑定版本。

建议路由：

```text
/routebooks/{id}               当前编辑页
/routebooks/{id}/versions/{id} 历史版本页
/share/{public_token}          最终分享页
```

最终页至少记录：

- `routebook_id`；
- `routebook_version_id`；
- `public_token`；
- `privacy_policy`；
- `created_at`；
- `revoked_at`。

后续草稿修改不会覆盖已生成的最终页面。

## 18. 失败与恢复

| 场景 | 处理方式 |
| --- | --- |
| LLM 输出无法校验 | 有限修复，仍失败则请求澄清 |
| 地点无结果 | 暂停流程，请用户补充行政区或地址 |
| 地点多候选 | 保存候选并中断等待确认 |
| 路线查询失败 | 保留地点，路线段标记 `unverified` |
| 天气查询失败 | 不阻断生成，标记 `unavailable` 或保留 `stale` |
| Worker 重启 | Celery 重投任务，LangGraph 从 checkpoint 恢复 |
| 重复任务 | 通过幂等键返回已有 Workflow Run 或结果 |
| 提案暂停期间版本变化 | 返回 `VERSION_CONFLICT`，重新计算提案 |
| 正式提交失败 | 事务回滚，不切换当前版本 |
| 最终页面渲染失败 | 保留正式版本和 final 记录，允许重试渲染 |

## 19. 安全与隐私

- 所有 API Key 仅从服务端环境变量读取；
- 高德 Web 服务 Key 不进入浏览器；
- 前端地图使用独立的浏览器端地图凭证和对应安全配置；
- 日志和追踪数据进行字段级脱敏；
- 分享页面默认隐藏精确住宅地址；
- 公开 token 使用足够长度的随机不可枚举值；
- 用户备注只属于当前路书，不建立长期用户画像；
- LLM 输入只发送完成任务所必需的数据；
- Graph checkpoint 不保存供应商密钥和完整敏感原始响应；
- 管理接口和分享接口使用不同的访问控制边界。

## 21. 测试策略

### 21.1 领域单元测试

覆盖：

- 必填需求判断；
- 状态迁移；
- 必去和排除约束；
- 重要修改确认规则；
- 影响范围计算；
- 未受影响日期保持不变；
- 版本递增和撤销；

- POI 类别白名单、黑名单和风险词惩罚；
- POI 候选打分、分差阈值和泛指概念禁止自动采用；
- 推荐反馈只影响当前路书；
- 行程修复不删除必去地点、不加入排除地点且在上限内终止。

### 21.2 Graph 测试

每个节点使用假 LLM 和假供应商测试：

- 正常路由；
- 中断负载；
- 恢复后的下一节点；
- 节点重复执行幂等性；
- 部分并行节点失败；
- checkpoint 恢复；
- 基础版本变化导致的冲突。

### 21.3 适配器契约测试

- 使用保存的脱敏响应样本验证字段映射；
- 对高德和和风错误码建立参数化测试；
- 使用少量真实凭证测试验证当前接口；
- 真实接口测试不在普通 CI 中默认运行。

### 21.4 端到端测试

使用 Playwright 覆盖需求第 14 节：

- 三日自驾创建；
- 缺失信息补问；
- 重名地点确认；
- 搜索“八达岭长城”时直通车、车站、停车场和游客中心不得作为景区主体自动采用；
- 用户只说“长城”时进入偏好选择而非静默选择某一景区；
- 用户拒绝远郊推荐后不再连续推荐同类远郊景点；
- 唯一候选但 POI 类别不符时不自动采用；
- 地图与行程联动；
- 第二天地点替换；
- 重要修改确认；
- 新版本生成和撤销；
- 最终页面绑定版本；
- 地点、路线和天气失败降级；
- 页面和日志不出现 API Key。

一期以 LangGraph 作为流程编排基础，可以直接支持地点消歧、重要修改确认、暂停恢复、外部接口降级和后续子流程扩展。

同时必须维持三层边界：

> LangGraph 决定流程下一步，领域服务决定业务是否允许，PostgreSQL 不可变版本决定用户最终看到的正式事实。

该边界是后续扩展酒店、票务、预算、多人协作及更多数据供应商时保持系统可测试、可恢复和数据一致的基础。
