# 路书 Agent 数据源获取分析

> 版本：V0.1
> 日期：2026-08-07
> 范围：MVP 数据需求、候选来源、获取策略与验证计划

## 1. 分析结论

首期建议将覆盖范围明确为：**中国境内、基于地点与道路并带基础天气信息的最小路线规划**。

MVP 的首要目标是跑通“对话收集需求 → 生成结构化路书 → 地图展示 → 局部修改 → 保存版本”闭环，而不是覆盖完整旅游事实。凡是没有稳定、正式接口的数据域，首版不进入自动规划和验收范围。

数据接入按三层建设：

1. **基础规划层（P0）**：地点检索、地理编码、路线距离与耗时、行政区划。优先使用高德开放平台，并保持地图展示、POI 和路径规划来自同一坐标体系。
2. **基础天气层（P0）**：通过和风天气 API 获取逐日/逐小时预报及灾害预警。天气失败允许降级，不阻断路线生成。
3. **其他动态增强层（MVP 后）**：景点开放时间、预约要求、价格和交通班次。只有获得稳定正式接口后才接入。
4. **可信度层（P0）**：保存来源 URL、提供方、查询时间、适用日期、原始值、规范化值、置信度和过期时间。数据不可得时允许降级，但不得伪装成已验证事实。

不建议 MVP 通过网页爬虫建立对 12306、OTA、酒店和景区预约平台的强依赖。这些来源常有登录、验证码、反自动化、条款和页面结构变化问题，无法满足需求中的可靠性和可追溯性要求。

### 1.1 最小功能边界

MVP 保留：

- 从自然语言提取出发地、目的地、日期/天数、交通方式、必去地点和排除地点；
- 通过稳定地图接口检索地点并取得坐标；
- 生成按天组织的地点顺序和路线段；
- 计算地图接口可返回的距离与预计耗时；
- 查询行程日期和主要地点对应的基础天气与灾害预警；
- 展示地图标记、路线和每日行程；
- 通过对话增加、删除、替换地点，或调整某一天；
- 重要修改确认、版本保存和最近一次撤销；
- 对缺少坐标、路线不通、日期不连续、必去项遗漏进行检查。

MVP 删除或降级：

- 不自动判断景点开放时间、闭馆日、票价和预约要求；
- 不查询火车、航班实时班次、余票和状态；
- 不查询酒店实时房态和价格；
- 不做精确预算，只允许用户填写备注或粗略总预算；
- 不提供实时道路管制、拥堵预测和专业安全判断；
- 不承诺餐厅营业、充电桩可用或加油站实时状态；
- 不因缺少上述数据阻止路书生成，仅在页面统一提示用户自行核实。

## 3. 候选数据源

### 3.1 地图、POI 与路线

#### 方案 A：高德开放平台（首选）

可覆盖地理/逆地理编码、POI、行政区划和驾车/步行/公交路径规划，适合中国境内 MVP。路径规划 2.0 需要申请 Web 服务 Key，并支持按需返回路线字段。

优势：

- 国内地点和道路覆盖较适合目标场景；
- POI、路径和前端地图可以维持同一供应商与 GCJ-02 坐标体系；
- 一套适配器即可支持城市自由行和自驾的主流程。

风险：

- 配额、商用授权和可缓存字段需在注册应用后逐项确认；
- POI 营业时间、票价和预约信息不能假设完整、实时；
- 路径耗时是查询时刻或服务模型的结果，未来日期不应表达为精确承诺。

#### 方案 B：百度地图（备选）

Web 服务 API 支持地点检索、地理编码和路线规划，可作为高德的替代供应商或故障降级来源。

主要问题是 BD-09 与高德 GCJ-02 不同。如果地图展示、地点和路线混用供应商，会造成坐标偏移与对象重复，因此 MVP 不建议同时作为主链路。

#### 方案 C：OpenStreetMap（境外扩展或自托管储备）

OSM 适合后续境外覆盖和开放数据补充，但公共 Nominatim 明确限制重度使用，绝对上限为每秒 1 次，并要求有效 User-Agent/Referer 和署名。它不适合作为生产系统的无约束公共后端；规模化使用需选择商业托管或自建 Nominatim/路由服务。

### 3.2 天气

建议首选和风天气作为独立适配器。官方文档提供实况、逐小时、逐日预报、空气质量、灾害预警、分钟级降水和生活指数等数据。

MVP 先取：

- 未来逐日预报，用于每日行程风险；
- 未来逐小时预报，用于近期行程时段调整；
- 灾害预警，用于阻断或高优先级风险提示；
- `observed_at`、`fetched_at`、`forecast_for` 和供应商更新时间。

超过可靠预报窗口的远期行程只展示季节性提示，不应把长期天气当作已验证事实。

### 3.3 景点与旅游内容

文化和旅游部数据服务可作为权威名录和景区等级来源。目前可查国家 5A 级旅游景区、五星级旅游饭店、国家级旅游休闲街区等数据，但它不是完整的实时营业、门票和预约 API。

景点数据建议分层合并：

1. 地图 POI：名称、位置、分类和基础联系方式；
2. 文旅部门：等级、官方名录与权威属性；
3. 景区官网/官方公众号：营业时间、闭馆日、门票和预约规则；
4. 用户确认或人工录入：无法稳定结构化获取的信息。

文化和旅游部资料显示重点景区预约已广泛采用分时预约，因此“是否需要预约”不能只作为普通描述字段，应进入冲突检查，并保存官方预约入口和查询时间。

### 3.4 铁路、航班与住宿

这三类是 MVP 的受限数据域：

- **铁路**：未发现面向普通开发者、稳定承诺的 12306 公共开放 API。不要把网页内部接口视为正式数据合同。
- **航班**：民航公共数据存在特定使用范围；面向旅客的实时航班数据通常需要航空公司、机场或商业数据服务逐一接入。
- **住宿**：实时房态和成交价格通常属于 OTA/酒店商业库存，需要合作授权；地图 POI 只能提供位置和基础属性，不能代表可订或当前价格。

MVP 降级策略：

- 用户录入已预订班次/酒店，系统对时间和地点做一致性检查；
- 提供官方查询或预订入口，由用户确认结果；
- 未获授权前只给价格区间估算，并标为 `estimated`；
- 班次、余票、房态一律带 `fetched_at` 和短有效期；
- 不自动下单，不声称余票或库存确定可用。

### 3.5 道路管制与安全风险

道路临时管制、景区闭园、高海拔和恶劣天气风险没有单一全国统一接口。MVP 采用组合策略：天气预警 + 路径服务返回结果 + 当地交管/文旅/景区官方公告链接 + 用户复核提示。

安全信息必须带适用时间和地域，无法验证时标注 `unverified`，不得由模型补全为事实。

## 4. 统一数据模型建议

每条外部事实至少包含：

```json
{
  "subject_id": "place_or_segment_id",
  "fact_type": "opening_hours",
  "value": {},
  "status": "verified|estimated|inferred|unverified|stale|conflicted",
  "provider": "provider_name",
  "source_url": "https://example.com/source",
  "source_record_id": "optional",
  "fetched_at": "2026-08-07T10:00:00+08:00",
  "valid_from": "2026-10-01T00:00:00+08:00",
  "valid_until": "2026-10-01T23:59:59+08:00",
  "coordinate_system": "GCJ-02",
  "confidence": 0.9,
  "raw_snapshot_ref": "optional_internal_reference"
}
```

地点对象不要仅用名称关联，应保留内部 `place_id`、供应商 ID、规范名、别名、行政区和坐标。不同供应商对象合并必须经过名称、距离、地址和类别联合匹配。

## 5. 获取架构

建议所有外部数据通过供应商适配器进入统一层：

```text
Agent / Planner
      |
Data Query Service
      |
Provider adapters (map / weather / tourism / transport)
      |
Normalization -> provenance -> cache -> freshness policy
      |
RouteBook structured configuration
```

关键规则：

- Agent 不直接拼接第三方接口响应进入路书；
- 原始响应与规范化结果分开保存；
- 缓存键包含供应商、接口、规范化参数和坐标系；
- 每类事实配置不同 TTL，静态名录可按月，路径按规划需要刷新，天气和班次按小时或更短；
- 查询失败返回显式状态，不覆盖上一版仍有效事实；
- 供应商 Key 只能在服务端使用，不进入前端路书配置或日志。

## 6. MVP 获取优先级

### 第一阶段：可生成基础路书

1. 高德：关键字检索、地点详情、地理编码、驾车/步行路径；
2. 坐标系与地点去重规范；
3. 路径距离/耗时写入行程段；
4. 来源、查询时间和失败降级字段；
5. 用“武汉—川西 7 天自驾”作为端到端验证样例。

### 第二阶段：接入基础天气

1. 接入和风天气逐日/逐小时预报与灾害预警；
2. 按行程日的主要停留地点查询，避免对同一天所有 POI 重复请求；
3. 展示查询时间、预报适用时间和陈旧状态；
4. 天气接口失败时降级，不阻断基础路线；
5. 恶劣天气只生成风险提示和调整建议，不自动覆盖已确认行程。

### 第三阶段：闭环稳定后按需增强

1. 景区事实优先采用用户录入，不建设通用爬虫；
2. 获得稳定接口后再加入开放时间和预约冲突检查；
3. 新数据域必须具备来源、时效和失败降级能力后才能进入正式路书。

### 第四阶段：商业接口明确后再评估

1. 评估铁路、航班、酒店商业合作接口；
2. 未获得正式授权前不开发自动查询；
3. 即使后续接入，也不得将估算价格表达为实时报价。

## 7. 首轮技术验证清单

- [ ] 申请高德测试 Key，核实各接口当前配额、商用条款和缓存限制；
- [ ] 对 20 个中文景点名称测试 POI 唯一性、别名和行政区消歧；
- [ ] 对驾车、步行和公交各测试 10 条路线，记录距离/耗时字段完整性；
- [ ] 验证途经点上限、跨省长路线、无结果和限流错误；
- [ ] 申请天气测试凭证，验证经纬度查询、逐小时/逐日和预警覆盖；
- [ ] 建立坐标系测试，禁止 GCJ-02、BD-09、WGS-84 静默混用；
- [ ] 定义各数据域 TTL、重试、熔断和陈旧数据策略；
- [ ] 确认第三方数据在分享页、导出页和缓存中的授权边界；
- [ ] 为所有动态数据展示“查询于”和“建议复核”状态；
- [ ] 选取 3 类样例验收：城市自由行、跨城自驾、含已订交通的商务行程。

## 8. 仍需产品确认

1. MVP 是否正式限定中国大陆；
2. 首发是否只验收自驾/步行路线，暂不验收公共交通；
3. 地图服务选定高德后，是否接受 MVP 不提供跨供应商降级；
4. 是否计划商业化；这会直接影响地图数据的授权方案；
5. 是否要求分享页面长期公开；第三方地图的展示授权需要单独核实。
