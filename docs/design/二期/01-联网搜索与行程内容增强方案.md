# 路书 Agent 二期联网搜索与行程内容增强方案

> 文档版本：V1.0  
> 文档状态：实施方案  
> 更新日期：2026-08-21  
> 适用阶段：二期第一个功能点开发与验收  
> 关联文档：`../一期/02-一期技术方案.md`、`../一期/04-一期交互优化方案.md`  
> 首版搜索能力：智谱 `webSearchPrime` MCP

## 1. 文档目的

本文定义路书 Agent 二期第一个功能点：在分日路线确认后，针对路线中的重点地点执行有限次数的联网搜索，从搜索结果中提取少量、有明确证据且能帮助用户执行行程的信息，并将其展示在现有右侧完整分日路线页面中。

本文重点规定：

- 联网搜索的触发时机、查询预算、地点优先级和停止条件；
- 智谱 `webSearchPrime` MCP 的接入边界及内部适配层；
- 开放时间、门票、预约、游玩攻略、美食和 Tips 的提取规则；
- “只展示确定信息”的证据、冲突与缺失处理；
- 缓存、去重、异步执行、版本化和降级策略；
- 分日路线页固定高度双栏地点行和 Popover 完整内容交互；
- 测试、评测、监控、验收标准和分阶段实施顺序。

本文不改变一期的地点解析、路线规划、天气、不可变版本和最终分享页原则。联网增强是附加能力，失败或无结果不得阻断路线生成与展示。

## 2. 背景与当前问题

一期已经形成以下稳定数据关系：

```text
RouteBookSnapshot
├── places
├── days_plan
│   ├── place_ids
│   ├── segment_ids
│   └── weather_refs
├── route_segments
├── weather
└── warnings
```

现有分日页面可以展示地点顺序、路线距离、预计耗时、天气与预警，但缺少用户真正执行行程时经常需要的信息：

- 景点开放时间、闭馆日和停止入场时间；
- 门票价格、预约要求与官方入口；
- 建议游玩时长、简短游览顺序和关键注意事项；
- 当日用餐区域或少量美食建议；
- 与当天路线、天气和地点特点相关的 Tips。

同时存在三类约束：

1. 地点数量可能较多，不能按“地点数 × 内容类型”无限搜索；
2. 搜索结果可能缺失、过期或互相冲突，不能为了填满栏目而推断；
3. 当前右侧页面高度和宽度有限，不能将每个地点扩展成长篇卡片。

因此二期首个功能点不追求“每个地点都有完整百科”，而是实现有预算、可追溯、稀疏展示的路线内容增强。

## 3. 目标与非目标

### 3.1 产品目标

1. 路线生成后自动增强重点地点，不阻塞路线首屏展示。
2. 每个地点最多展示 3～5 条最有行动价值的信息。
3. 只有具备明确来源和适用性的内容才能展示。
4. 没有搜到的字段不显示“未知”“暂无”或“以官方为准”。
5. 控制一份普通路书的搜索次数、延迟和调用成本。
6. 路线顺序调整时复用地点内容，只刷新真正受影响的数据。
7. 在现有右侧分日路线页中直接展示攻略摘要，完整内容通过 Popover 查看。
8. MCP不可用、超时或额度耗尽时，原有路线能力保持正常。

### 3.2 首版非目标

- 不为所有地点生成完整百科介绍；
- 不保证门票、开放时间、攻略、美食等栏目齐全；
- 不对每个地点分别执行门票、开放时间、美食和 Tips 查询；
- 不进行无限补搜或多搜索引擎并行召回；
- 不将普通网页摘要直接标记为官方事实；
- 不自动购买门票、预约或跳转执行外部交易；
- 不接入 Tavily、Serper、Brave 或自建 SearXNG；
- 不以个人 Coding Plan MCP 作为未来多租户生产规模的永久承诺；
- 不在首版实现复杂的用户长期美食偏好画像。

## 4. 核心设计原则

1. **证据驱动的稀疏展示**：搜索是为了发现少量确定信息，不是为了填满固定栏目。
2. **缺失即缺省**：没有证据的字段保持 `null`，前端不渲染。
3. **模型只做提取和压缩**：LLM 不得根据常识或相似地点补全事实。
4. **关键事实高门槛**：门票、开放时间、闭馆日、预约必须采用更严格的来源规则。
5. **查询有硬预算**：任何工作流、地点和内容类型都必须受调用次数上限控制。
6. **先缓存再联网**：地点不变时优先复用，路线顺序变化不触发地点重新搜索。
7. **路线与增强解耦**：路线成功不依赖增强成功，增强失败不回滚路线版本。
8. **版本可追溯**：展示内容必须绑定来源、查询时间和明确路书版本。
9. **摘要直接可读，全文按需查看**：页面保持固定节奏，完整攻略进入 Popover。
10. **供应商可替换**：业务层依赖内部 `SearchProvider`，不直接依赖 MCP 原始协议。

## 5. 功能范围与信息层级

### 5.1 地点级内容

地点内容通过 `place_id` 关联，允许包含：

- 开放时间；
- 停止售票或停止入场时间；
- 明确票价；
- 是否需要预约及预约要求；
- 建议游玩时长；
- 80～180 字的主要游玩攻略；
- 最多 2～3 条关键 Tips；
- 最多一个主要来源和两个补充来源。

字段不是必填项。一个地点可以只有一条预约提示，也可以没有任何增强内容。

### 5.2 当日级内容

首版保留以下当日聚合能力：

- 天气与预警汇总为一行；
- 当天地点顺序、总距离和交通耗时摘要；
- 最多三条有依据的当日重点提示；
- 后续可加入午餐、晚餐各一个主选和一个备选。

### 5.3 路线段级内容

继续使用现有 `route_segments` 展示：

- 下一站名称；
- 交通方式；
- 距离；
- 预计耗时。

如果搜索结果中存在明确入口、出口或换乘提示，可作为路线段增强内容；没有明确证据时不生成。

## 6. 地点优先级与查询范围

### 6.1 优先级

系统根据现有 `semantic_type`、`category_normalized` 和确定性规则对地点分类，不为分类调用 LLM。

| 优先级 | 典型地点 | 自动查询内容 | 首版行为 |
| --- | --- | --- | --- |
| P0 | 景区、博物馆、乐园、演出、预约制场所 | 开放、闭馆、门票、预约、时长、强提醒 | 自动查询 |
| P1 | 公园、寺庙、观景台、特色市场 | 开放、收费、时长、重要 Tips | 预算充足时查询 |
| P2 | 商圈、街区、车站、酒店、集合点 | 不主动查询 | 使用一期已有事实 |
| P3 | 餐厅、咖啡馆、小吃 | 不逐地点查询 | 后续按每日用餐区域聚合 |

### 6.2 查询上限

首版默认预算：

```python
class EnrichmentBudget:
    max_search_requests: int = 12
    max_places_enriched: int = 12
    max_searches_per_place: int = 1
    max_results_per_search: int = 5
    max_llm_extract_calls: int = 2
    max_llm_copy_calls: int = 1
    max_retry_count: int = 0
```

补充规则：

- 优先消费 P0，再消费 P1；
- 每个地点默认仅允许一次综合搜索；
- 首版不为缺失字段单独补搜；
- 超时、空结果和低质量结果均计入一次调用；
- 达到预算后停止后续查询，已完成内容正常保存；
- 预算用尽不产生用户可见错误卡片。

### 6.3 综合查询模板

默认查询：

```text
{城市} {地点全名} 官方 开放时间 停止入场 门票 预约 参观须知 游玩建议
```

查询必须包含城市和经过一期地点消歧的完整名称。不得只使用“博物馆”“古镇”“公园”等泛指名称。

## 7. 智谱 webSearchPrime MCP 接入

### 7.1 首版选择

二期首版只使用智谱 Coding Plan 提供的 Remote MCP：

```text
https://open.bigmodel.cn/api/mcp/web_search_prime/mcp
```

工具：

```text
webSearchPrime
```

预期返回至少包含网页标题、URL、摘要、网站名称等搜索结果信息。

### 7.2 适配层

业务服务不得直接依赖 MCP 原始返回，统一通过：

```text
PlaceEnrichmentService
        ↓
SearchProvider Protocol
        ↓
ZhipuWebSearchPrimeProvider
        ↓
智谱 Remote MCP
```

建议内部接口：

```python
class SearchProvider(Protocol):
    def search(self, request: SearchRequest) -> SearchResponse: ...


class SearchRequest(BaseModel):
    query: str
    max_results: int = 5
    request_id: str
    routebook_id: UUID
    place_id: UUID


class SearchResult(BaseModel):
    title: str
    url: str
    snippet: str
    site_name: str | None = None
    published_at: datetime | None = None
    rank: int
```

### 7.3 凭证与日志

- MCP Key 仅保存在服务端部署环境；
- 前端、路书快照和分享页不得包含 Key；
- Authorization Header 不得写入日志；
- 日志记录 `request_id`、地点、耗时、结果数和错误类型，不记录凭证；
- `.env.example` 只提交变量名和说明。

### 7.4 超时与重试

建议：

- 连接与单次调用总超时由 Provider 配置；
- 首版搜索失败不自动重试；
- 鉴权失败立即停止当前增强任务并告警；
- 限流或额度耗尽立即熔断本次任务剩余搜索；
- 单地点失败不得影响其他已完成地点和原路线版本。

## 8. 搜索、提取与筛选流程

### 8.1 总流程

```text
路线版本提交成功
    ↓
创建内容增强 Workflow Run
    ↓
加载当前版本与地点
    ↓
按 P0/P1 排序并检查缓存
    ├── 有有效缓存 → 复用
    └── 无有效缓存 → 消费预算调用 webSearchPrime
                         ↓
                    地点身份校验
                         ↓
                    结果来源分类
                         ↓
                    结构化事实提取
                         ↓
                    证据与冲突校验
                         ↓
                    生成短摘要和攻略文案
                         ↓
                    保存地点增强结果
    ↓
聚合天气、当日摘要与路线展示数据
    ↓
提交增强版本并通知前端刷新
```

### 8.2 地点身份校验

搜索结果进入提取前必须验证：

- 标题或摘要明确指向当前地点；
- 城市、行政区或地址与当前 `PlaceSnapshot` 不冲突；
- 不得将同名异地景点、入口、停车场、票务代理或旅行社页面作为景点主体；
- 无法确认地点身份时丢弃该结果。

### 8.3 来源分类

来源至少分为：

```text
official
government
trusted_travel_platform
content_platform
unknown
```

判定优先使用域名白名单、网站名称和确定性规则。LLM 可辅助分类，但不得单独决定“官方”。

### 8.4 强事实与体验信息

强事实包括：

- 开放时间；
- 闭馆日；
- 停止售票或停止入场；
- 门票价格；
- 预约要求；
- 临时关闭、限流等公告。

强事实规则：

- 官方或政府来源优先；
- 非官方来源必须满足更高证据门槛；
- 来源冲突且无法确定时不展示；
- 旧年份或与出行日期不匹配的信息不展示；
- 搜索摘要未明确给出具体结论时不推断。

体验信息包括：

- 建议游玩时长；
- 推荐游览顺序；
- 拍照、排队、入口出口和体力提示；
- 少量美食与休息建议。

体验信息可以来自可信旅游平台，但必须明确对应当前地点，且文案不得增加来源中不存在的事实。

### 8.5 LLM 提取约束

结构化提取提示词必须包含：

```text
只提取搜索结果中明确存在的信息。

禁止：
1. 根据常识补充缺失字段；
2. 根据相似地点推断；
3. 将“通常”“可能”改写为确定事实；
4. 将搜索标题中的年份忽略；
5. 在来源冲突时自行选择无依据结论；
6. 为了填满输出数量生成内容。

没有可靠证据的字段返回 null。
highlights 允许为空，最多输出 5 条。
```

LLM 输出必须通过 Pydantic Schema 校验。校验失败时丢弃本批结果，不得保存自由文本作为正式内容。

## 9. 数据模型

### 9.1 建议快照结构

避免持续扩展 `PlaceSnapshot`，新增独立增强集合：

```python
class ContentSourceSnapshot(ApiModel):
    id: str
    title: str
    url: str
    site_name: str | None
    source_type: str
    published_at: datetime | None
    retrieved_at: datetime


class PlaceHighlightSnapshot(ApiModel):
    type: Literal[
        "closure",
        "opening_hours",
        "last_entry",
        "ticket",
        "reservation",
        "duration",
        "tip",
    ]
    label: str
    text: str
    source_ids: list[str]
    confidence: float
    status: FactStatus


class PlaceEnrichmentSnapshot(ApiModel):
    place_id: UUID
    summary: str | None
    guide_text: str | None
    highlights: list[PlaceHighlightSnapshot]
    tips: list[PlaceHighlightSnapshot]
    sources: list[ContentSourceSnapshot]
    generated_at: datetime
    expires_at: datetime | None
    status: FactStatus
```

路书快照增加：

```python
place_enrichments: list[PlaceEnrichmentSnapshot]
```

前端通过 `place_id` 将其挂载到对应分日地点。

## 10. 缓存、去重与失效

### 10.1 缓存键

```text
provider
+ provider_place_id
+ destination_city
+ travel_date_bucket
+ enrichment_schema_version
```

同一路书内使用 `place_id` 关联，跨路书复用使用供应商地点 ID 和城市防止误匹配。

### 10.2 建议有效期

| 内容 | 建议有效期 |
| --- | ---: |
| 基础介绍、玩法亮点 | 60～90 天 |
| 建议游玩时长 | 30 天 |
| 常规开放时间 | 7 天 |
| 门票、预约规则 | 3～7 天 |
| 临时关闭与节假日公告 | 6～12 小时 |
| 美食建议 | 14 天 |
| 当日攻略文案 | 跟随路书版本 |

首版如果 MCP 摘要无法可靠识别内容类型，可按整条地点增强结果使用较短统一有效期，后续再拆分字段级 TTL。

### 10.3 局部失效

- 只调整地点顺序：全部复用；
- 修改某天节奏：地点事实复用，重新生成当日摘要；
- 新增地点：只查询新地点；
- 删除地点：不重新查询其他地点；
- 修改出行日期：刷新日期敏感事实；
- 地点身份或供应商 ID 变化：旧缓存不得复用。

## 11. 异步任务、状态与版本

### 11.1 触发时机

分日路线版本提交成功后触发独立增强任务：

```text
ITINERARY_READY
    ↓
ENRICHING_CONTENT
    ↓
ENRICHMENT_READY
```

页面先显示原路线，再通过现有 SSE 机制接收进度并刷新增强版本。

### 11.2 进度文案

```text
正在整理旅行信息 · 3/8 个地点
正在核验“北京警察博物馆”的参观信息
已完成主要地点攻略整理
```

不得向用户展示模型思维链、原始搜索查询或供应商内部错误。

### 11.3 版本策略

建议：

1. 路线规划提交版本 `vN`；
2. 增强任务以 `vN` 为固定输入；
3. 增强完成后提交 `vN+1`，变更摘要为“补充地点开放、预约与游玩提示”；
4. 如果任务完成时当前版本已经发生不兼容修改，不覆盖当前版本；
5. 未变化地点的有效增强内容可复制到后续版本；
6. 最终分享页绑定包含增强内容的不可变版本。

### 11.4 降级

以下情况均不阻断路线：

- MCP 超时；
- MCP 返回空结果；
- 搜索结果无法确认地点身份；
- 所有候选来源冲突；
- LLM 结构化提取失败；
- MCP额度耗尽或限流；
- 单地点无可靠内容。

降级结果为原有路线页面，不显示增强失败卡片。

## 12. 分日路线页面布局

### 12.1 总体原则

不将地点扩展成长篇纵向卡片。右侧保留现有分日路线结构，将每个地点改造成固定节奏的双栏横条：

```text
┌────┬──────────────────────┬────────────────────────────────┬───┐
│ 01 │ 日坛公园             │ 游玩攻略                       │ ⓘ │
│    │ 朝阳区 · 公园        │ 建议从北门进入，沿核心景观区…  │   │
│    │ 多云 23–31℃          │ Tips：雨后石阶可能湿滑……       │   │
│    │ ↓ 5.1km · 约32分钟   │ 开放 06:00–21:00 · 免费        │   │
└────┴──────────────────────┴────────────────────────────────┴───┘
```

建议桌面端列宽：

- 路线编号：42px；
- 左侧地点、天气与路线：约 35%；
- 右侧攻略摘要：剩余空间；
- Popover 图标：32～40px。

左右区域使用一条细竖线分隔，不新增嵌套卡片和重阴影。

### 12.2 地点行高度

桌面端目标：

```text
min-height: 118px
max-height: 132px
```

不建议使用绝对固定高度裁剪字体，使用最大高度配合文本截断。移动端改为上下排列，高度允许增长到约 144～156px。

### 12.3 左侧路线事实

显示优先级：

1. 地点名称；
2. 行政区和地点类型；
3. 与该地点直接相关的天气差异；
4. 下一段路线距离和时间。

最后一个地点显示“今日最后一站”，不生成空路线连接器。

### 12.4 天气与预警聚合

当前多个地点的天气卡片改为顶部一行：

```text
☁ 多云 23–31℃   ⚠ 雷电蓝色预警 · 朝阳区、东城区
```

聚合规则：

- 相同天气只展示一次；
- 相同预警标题去重；
- 同一预警覆盖多个区时合并区县；
- 主行最多显示最高等级或最重要的一条预警；
- 其余预警通过展开内容查看；
- 地点天气与顶部完全相同时，不在地点行重复展示。

### 12.5 右侧攻略摘要

右侧最多展示：

- 两行主要攻略；
- 一行关键事实；
- 一行 Tips。

没有对应内容时不保留空行。建议文案限制：

| 内容 | 页面摘要限制 | 完整内容限制 |
| --- | --- | --- |
| 攻略摘要 | 最多 2 行 | 80～180 字 |
| 关键事实 | 最多 1 行 | 最多 5 条 |
| Tips | 最多 1 行 | 最多 3 条 |
| 地点亮点 | 最多 50 字 | 最多 100 字 |

多行省略示例：

```css
.guide-summary {
  display: -webkit-box;
  overflow: hidden;
  -webkit-box-orient: vertical;
  -webkit-line-clamp: 2;
}
```

只要存在未完整展示的 `guide_text`、更多 highlights、Tips 或来源，就显示详情图标。

## 13. 攻略 Popover

### 13.1 内容

Popover 展示：

```text
地点名称 · 游玩攻略

建议玩法
完整攻略正文

关键信息
仅展示已确认的开放、预约、门票、时长等

Tips
最多三条

来源与查询时间
```

建议尺寸：

```text
宽度：380～460px
最大高度：360～440px
超出：Popover 内部滚动
```

### 13.2 交互

因为 Popover 包含长文和来源链接，它不是普通 Tooltip，应采用可交互内容面板：

- 鼠标移入图标，约 150ms 后打开；
- 鼠标移入 Popover 后保持打开；
- 同时离开图标和 Popover，约 200ms 后关闭；
- 点击图标后固定打开；
- 再次点击、点击外部或按 `Escape` 关闭；
- 键盘聚焦图标可打开；
- 移动端点击打开；
- Popover 内部链接可以正常聚焦和点击。

推荐使用原生 `popover="auto"` 进入 top layer，并提供定位降级。不得实现只能悬停访问的内容。

### 13.3 定位与边界

- 默认显示在详情图标靠近正文的一侧；
- 靠近窗口右侧时水平翻转；
- 靠近底部时垂直翻转；
- 不得被 `.itinerary-panel` 的滚动容器裁剪；
- 不支持锚点定位的环境使用受控 `position: fixed` 和边界计算降级；
- Popover 箭头为装饰性元素，不进入无障碍树。

## 14. 前端组件建议

在现有 `routebook-workspace.tsx` 基础上拆分：

```text
DayFacts
└── DayWeatherSummary

DayItinerary
├── PlaceRouteRow
│   ├── PlaceRouteFacts
│   ├── PlaceGuideSummary
│   └── PlaceGuidePopover
└── RouteConnector
```

前端只渲染服务端筛选完成的增强内容，不在浏览器中重新判断来源可信度。

建议状态：

```typescript
type PlaceGuidePopoverState = {
  openPlaceId: string | null;
  pinned: boolean;
};
```

同一时刻最多打开一个地点 Popover，避免重叠和额外渲染。

## 15. 性能要求

### 15.1 服务端

- 一份路书搜索次数不超过配置预算；
- 搜索请求使用有限并发，避免瞬时触发 MCP 限流；
- 相同缓存键使用 single-flight，防止并发重复查询；
- LLM 按批次提取多个地点，避免每地点一次模型调用；
- 原始 MCP 响应只保存必要字段，不长期保存无关大文本；
- 增强任务失败不触发 Celery 无限重投。

### 15.2 前端

- 只渲染当前选中日期；
- 同一时间只渲染一个打开的 Popover；
- 隐藏日期不预加载 Popover 正文中的外部资源；
- 长列表地点行保持稳定 key；
- 首屏以外的复杂地点内容可使用 `content-visibility: auto`，并配合 `contain-intrinsic-size` 防止滚动跳动；
- 日期切换和 Popover 打开不得触发整个工作区重复布局。

## 16. API 与事件建议

在现有路书读取结构中返回增强版本即可。若需要独立刷新，可增加：

```http
POST /api/routebooks/{routebook_id}/enrichments
```

返回现有异步约定：

```json
{
  "workflow_run_id": "...",
  "workflow_status": "queued",
  "events_url": "/api/workflow-runs/.../events"
}
```

进度阶段建议加入：

```text
selecting_enrichment_places
searching_place_information
extracting_place_facts
generating_place_copy
saving_enrichment_version
```

事件只包含阶段、已完成数量、总数和用户可读文案，不包含 MCP 凭证与原始敏感响应。

## 17. 错误与状态语义

| 情况 | 内部状态 | 页面行为 |
| --- | --- | --- |
| 有官方或足够证据 | `verified` | 展示 |
| 体验类内容来源可信但非强事实 | `unverified` 或专用建议状态 | 只作为攻略建议展示 |
| 缓存过期 | `stale` | 默认不展示日期敏感事实，后台可刷新 |
| 来源冲突 | `conflicted` | 不展示冲突字段 |
| 搜索无结果 | `unavailable` | 不显示增强内容 |
| MCP不可用 | 任务降级 | 保留原路线 |
| LLM输出校验失败 | 丢弃该批 | 保留原路线和其他成功地点 |

严禁将 `unavailable` 渲染为“门票未知”等占位内容。

## 18. 测试与评测

### 18.1 Provider 契约测试

- MCP 成功响应映射；
- 空结果；
- 超时；
- 鉴权失败；
- 限流或额度耗尽；
- 非法 URL 和缺失字段；
- 日志凭证脱敏。

### 18.2 提取与证据测试

- 官方摘要明确包含开放时间时正确提取；
- 没有票价时 `ticket` 保持 `null`；
- 同名异地地点不进入结果；
- 旧年份内容不用于当前日期；
- 两个来源票价冲突时不展示票价；
- “通常开放”不得转写为确定开放时间；
- 空 highlights 被视为正常结果；
- 每地点不超过 5 条 highlights 和 3 条 Tips。

### 18.3 预算与缓存测试

- P0 优先于 P1；
- 达到全局预算后不再调用 MCP；
- 每地点最多一次搜索；
- 相同地点跨版本缓存命中；
- 调整顺序不重新搜索；
- 新增地点只查询新增项；
- 并发相同缓存键只调用一次 Provider。

### 18.4 前端测试

- 天气和重复预警正确聚合；
- 无增强内容的地点保持原路线行；
- 攻略摘要按行截断；
- 有完整内容时显示详情按钮；
- Popover 可通过 hover、focus 和 click 打开；
- 鼠标移入 Popover 不会关闭；
- `Escape` 和外部点击关闭；
- 同时只打开一个 Popover；
- 移动端可点击访问完整内容；
- 键盘顺序和焦点状态可见；
- Popover 不被右侧滚动容器裁剪。

### 18.5 建议离线评测集

首版开发前建立 30～50 个国内地点样本，覆盖：

- 国家级景区；
- 市级博物馆；
- 免费公园；
- 预约制场所；
- 临时闭馆或季节开放地点；
- 同名异地地点；
- 只有非官方内容的小型地点；
- 无可靠搜索结果的地点。

核心指标：

| 指标 | 建议目标 |
| --- | ---: |
| 正确地点命中率 | ≥ 95% |
| 至少一条可展示信息的地点占比 | 仅统计，不设强制填充目标 |
| 强事实错误展示率 | 0 |
| 单地点平均搜索次数 | ≤ 1 |
| 单路书搜索次数 | ≤ 12 |
| 无结果正常降级率 | 100% |

## 19. 可观测性

建议记录：

- `enrichment_runs_total`；
- `enrichment_places_selected_total`；
- `web_search_prime_requests_total`；
- `web_search_prime_latency_ms`；
- `web_search_prime_empty_results_total`；
- `enrichment_cache_hit_total`；
- `enrichment_cache_miss_total`；
- `enrichment_highlights_persisted_total`；
- `enrichment_fields_dropped_conflict_total`；
- `enrichment_budget_exhausted_total`；
- `enrichment_provider_errors_total{type}`。

日志需要能够回答：

1. 某地点为什么没有展示内容；
2. 是否因为缓存、无结果、身份不符、证据不足或冲突被丢弃；
3. 每份路书消耗了多少次 MCP 调用；
4. 哪些地点类型最容易得到有效信息；
5. MCP延迟和失败是否影响增强完成率。

## 20. 安全与隐私

- 搜索查询只包含完成地点检索所需的城市、地点和公开旅行日期语义；
- 不将用户姓名、联系方式、私人地址和完整对话发送到搜索 MCP；
- 不将 MCP Key 返回前端；
- 外部 URL 在页面中显示目标网站名称并使用安全跳转属性；
- 页面不得执行搜索结果中的 HTML 或脚本；
- 摘要与攻略正文作为纯文本或经过严格白名单处理的 Markdown 渲染；
- 分享页按既有隐私策略处理地址，不因增强内容重新泄露精确地址。

## 21. 实施顺序

### 阶段 A：搜索与证据闭环

1. 增加 MCP 配置和 `SearchProvider`；
2. 实现 `ZhipuWebSearchPrimeProvider`；
3. 建立 30～50 个地点离线评测集；
4. 实现地点优先级、预算和缓存；
5. 实现结构化提取、证据筛选和空结果降级。

### 阶段 B：持久化与异步流程

1. 增加增强快照模型和契约；
2. 增加增强 Workflow Run 和进度阶段；
3. 保存增强版本；
4. 实现版本冲突、局部复用和失败降级；
5. 增加监控指标和运行日志。

### 阶段 C：分日页面展示

1. 将天气和预警聚合为一行；
2. 将地点列表改为固定高度双栏路线行；
3. 增加攻略摘要、多行省略和详情图标；
4. 增加可悬停、聚焦和点击的 Popover；
5. 完成桌面、移动端、键盘与滚动边界测试。

### 阶段 D：质量评测与上线

1. 跑离线地点集和错误注入；
2. 验证查询预算、缓存命中与 MCP 额度消耗；
3. 验证强事实零错误目标；
4. 小范围启用并观察无结果率、延迟和 Popover 使用率；
5. 根据数据决定是否接入标准 Web Search API 或备用 Provider。

## 22. 验收标准

### 22.1 搜索与内容

- [ ] 首版只调用智谱 `webSearchPrime` MCP；
- [ ] 每地点最多一次综合搜索；
- [ ] 普通路书最多 12 次搜索，可配置；
- [ ] 没有证据的字段保持为空且不展示；
- [ ] 来源冲突的强事实不展示；
- [ ] 每地点最多 5 条关键信息和 3 条 Tips；
- [ ] MCP失败时原路线仍可正常使用；
- [ ] 相同地点与有效日期范围内可以命中缓存。

### 22.2 页面

- [ ] 右侧直接展示攻略摘要；
- [ ] 地点行桌面端保持约 118～132px 的稳定高度；
- [ ] 左侧展示地点、差异天气和路线事实；
- [ ] 右侧展示攻略摘要、关键事实和单条 Tip；
- [ ] 超出内容使用多行省略；
- [ ] 详情图标可以通过悬停、键盘和点击打开 Popover；
- [ ] Popover 可滚动、可关闭、不会被父容器裁剪；
- [ ] 天气和重复预警聚合为一行；
- [ ] 无增强内容的地点不显示空栏目或错误提示。

### 22.3 工程质量

- [ ] Provider、提取、预算、缓存、异步流程和前端交互具备自动化测试；
- [ ] MCP Key 和 Authorization Header 不进入日志、快照和前端；
- [ ] 所有结构化内容通过 Pydantic 校验；
- [ ] 增强版本遵守一期不可变版本规则；
- [ ] SSE断开、页面刷新和 Worker失败后可以恢复或明确降级。

## 23. 后续演进

完成首版并取得实测数据后，再评估：

- 从 Coding Plan MCP 切换到智谱标准 Web Search API；
- 引入网页读取能力补充搜索摘要不足；
- 增加 Tavily Extract 或其他 Provider 作为受控备用；
- 按每日用餐区域生成午餐和晚餐节点；
- 支持用户手动刷新单个地点；
- 支持字段级 TTL 和局部更新；
- 在最终分享页中复用同一套地点摘要与 Popover；
- 根据用户点击数据调整自动展示内容的优先级。

是否演进由搜索命中率、错误率、平均调用次数、MCP额度消耗和用户实际展开率共同决定，不因字段缺失而盲目增加查询。
