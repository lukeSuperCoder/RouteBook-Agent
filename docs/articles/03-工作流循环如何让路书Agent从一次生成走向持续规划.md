## 一、为什么需要工作流循环

最小原型跑通以后，我很快遇到了一个问题：真实用户几乎不会在第一次输入时，就把旅行规划需要的所有条件说完整。

例如，用户可能只说：

```text
帮我规划一个北京三日游
```

系统暂时只能确定目的地是北京、旅行天数是三天，但可能还不知道：

- 什么时候出发；
- 从哪里出发；
- 自驾、公共交通还是步行；
- 喜欢历史、人文还是自然风景；
- 想轻松游还是紧凑游；
- 有没有必去或明确不想去的地方。

即使这些信息全部补齐，后面的规划过程仍然存在不确定性：

- 搜索“鼓楼”可能找到景区、地铁站、停车场和多个同名地点；
- 系统推荐的景点可能不符合用户的真实偏好；
- 用户选中的地点可能无法合理安排进三天；
- 行程生成以后，用户还可能继续要求增加、删除或替换地点。

所以，一份完整路书的生成过程并不是：

```text
用户输入 → AI 生成行程 → 结束
```

它更接近下面这条持续收敛的链路：

```text
用户输入
→ 理解需求
→ 检查信息是否完整
→ 信息不完整就继续追问
→ 搜索并推荐真实地点
→ 地点存在歧义就让用户选择
→ 生成分日行程
→ 检查路线和时间是否可行
→ 不可行就进入自动修复
→ 用户继续提出修改
→ 重新计算受影响的部分
→ 保存新的路书版本
```

这条链路里的每一次返回、等待、恢复和重新计算，都属于工作流循环。

如果每次都把全部上下文重新交给模型，让它从头生成一份新行程，会出现几个很明显的问题：

- 已经确认的信息可能被改掉；
- 用户拒绝过的地点可能再次出现；
- 一个地点变化，整份行程都跟着漂移；
- 路线不可行时，模型可能通过修改文字掩盖冲突；
- 请求失败后，很难知道应该从哪里继续。

因此，当前项目没有把旅行规划理解为一次模型调用，而是把它拆成了一组可以反复执行、暂停和恢复的工作流。

这里的“循环”也不只是在流程图里画一条回边。它的核心是保留已经确认的状态，在遇到信息缺失、地点歧义、路线冲突或用户修改时，回到正确的处理阶段继续推进，而不是推翻全部结果重新开始。

在当前项目中，循环机制主要参与四类工作：需求补问、地点推荐与确认、行程生成与修复，以及行程修改与局部重算。

## 二、需求补问循环：信息不完整时继续追问

需求工作流是目前最直接使用 LangGraph 循环的地方。

它的结构并不复杂：

```text
extract_requirement_patch
→ merge_requirements
→ 判断是否满足规划条件
    ├── 已满足 → END
    └── 未满足 → build_clarification
                    ↓ interrupt
                 等待用户回答
                    ↓ resume
              回到需求提取节点
```

模型每一轮只提取“本轮发生了什么变化”，而不是重新生成完整需求。普通代码再把增量合并到已经保存的需求快照中。

例如第一轮用户只说“9 月去北京玩三天”，系统会保留已经识别出的北京和三天，只针对真正阻断后续规划的信息提问。用户回答以后，工作流使用同一个 `thread_id` 恢复，继续处理新的回答。

核心图结构如下：

```python
builder.add_edge(START, "extract_requirement_patch")
builder.add_edge("extract_requirement_patch", "merge_requirements")
builder.add_conditional_edges(
    "merge_requirements",
    route_after_merge,
    {"ready": END, "clarify": "build_clarification"},
)
builder.add_edge("build_clarification", "extract_requirement_patch")
```

补问节点通过 `interrupt()` 暂停：

```python
answer_raw = interrupt({
    "kind": "requirement_clarification",
    "questions": questions,
    "requirements": current_requirements,
})
```

用户回答后，Worker 不会创建一张新图，而是用相同的工作流 ID 恢复原来的检查点：

```python
graph.invoke(
    Command(resume={
        "message_id": client_message_id,
        "text": message_text,
    }),
    config={"configurable": {"thread_id": workflow_run_id}},
)
```

这套循环起到的第一个作用，是让需求逐轮累积。已经确认的字段不会因为下一句话没有再次提到就消失。

第二个作用，是控制追问数量。当前领域服务最多返回三个阻断问题，不会为了追求一份“完美画像”，把所有可选偏好一次问完。普通偏好可以采用明确默认值，只有会阻止当前规划继续的信息才进入补问。

第三个作用，是给模型失败准备降级路径。如果结构化提取连续失败，系统不会把一段无法验证的文本直接写入需求，而是退回到确定性的补问，让用户补充关键字段。

## 三、推荐与确认循环：让地点选择逐步收敛

需求确认以后，系统会根据目的地、主题、节奏、远郊接受度和历史反馈构造推荐策略，再调用高德 POI 搜索召回真实地点。

这个环节同样不是“推荐一次就结束”，而是一个反馈循环：

```text
构造推荐策略
→ 多关键词召回真实 POI
→ 硬过滤、评分、去重和多样性选择
→ 用户接受 / 拒绝 / 要求替换
→ 保存本路书内的反馈
→ 下一轮推荐重新过滤和排序
```

用户可以接受某个候选，也可以用“不感兴趣”或“太远”等原因拒绝，还可以要求替换。被拒绝或替换的供应商 POI ID 会进入本次路书的反馈记录，下一轮召回时直接排除；“太远”等原因还会影响新的推荐策略。

这解决了一个很实际的问题：如果系统每次推荐都没有记忆，用户刚刚拒绝的地点很可能在下一批候选中再次出现。反馈循环让推荐结果随着用户选择逐渐收敛，但这些反馈目前只作用于当前路书，不会被擅自保存为跨项目的长期用户画像。

地点进入正式规划前还要经过确认策略。高置信、类别正确且没有语义风险的候选可以自动采用；多个合理候选则暂停等待用户选择。

例如“鼓楼”可能是景区、行政地名、地铁站，也可能是商户。工作流会把经过硬过滤和排序后的候选交给用户，而不是默认采用高德返回的第一条。选择完成后，再从检查点恢复地点解析流程。

因此，这一层循环实际完成了两件不同的事：推荐反馈负责让候选越来越符合偏好，地点消歧负责确保进入规划的是用户真正指向的真实 POI。

## 四、行程修复循环：生成以后还要验证

地点全部确认以后，系统才能进入分日规划。

当前规划器会先按行政区、优先级、每日容量和天气倾向分配地点，再使用最近邻与有限 2-opt 优化日内顺序，最后查询相邻地点之间的正式路线。

但“成功排进几天”不代表行程可行。系统还会检查：

- 必去地点是否全部出现；
- 排除地点是否混入；
- 每天地点数量是否超过节奏容量；
- 单日交通时间和总时长是否超限；
- 是否存在不合理的跨区安排；
- 路线事实是否可用。

所以规划阶段实现的是一个“生成—验证—修复”循环：

```text
生成分日方案
→ 查询路线并计算耗时
→ 校验约束
    ├── 通过 → 获取天气并提交
    ├── 可修复 → 调整分日或顺序 → 再次校验
    └── 不可修复 → 返回结构化冲突
```

实现上使用了一个有明确上限的循环：

```python
attempts = 0
while attempts <= 3:
    planned = route_days(arranged)
    conflicts = validate(planned, places, requirements)

    if not conflicts:
        return completed_result(planned)

    if has_blocking_conflict(conflicts) or attempts == 3:
        return infeasible_result(conflicts)

    arranged = repair(arranged, conflicts)
    attempts += 1
```

这里最重要的不是“自动重试三次”，而是修复边界。

系统可以调整地点所属日期、改变日内顺序，或者处理低优先级候选；但不能偷偷删除必去地点，不能加入用户明确排除的地点，也不能伪造距离和耗时让方案看起来可行。

三轮以后仍然无法满足约束，就返回 `repair_exhausted` 等结构化冲突。循环必须能够停止，否则 Agent 很容易在一个不可能完成的目标上反复消耗模型和地图接口。

## 五、编辑循环：用户修改后只重算受影响范围

旅行规划不会在第一版行程生成时结束。真正使用时，用户一定会继续修改：增加地点、删除地点、替换地点、调整某一天，或者改变旅行总天数。

因此，编辑流程形成了更长周期的业务循环：

```text
当前正式版本
→ 解析修改意图
→ 计算影响范围
→ 生成预览
→ 必要时等待用户确认
→ 只重算受影响的日期、路线和天气
→ 校验未影响日期没有变化
→ 提交一个新的不可变版本
→ 用户继续提出下一次修改
```

例如用户说“把第二天的 A 景点换成 B”，系统会先计算受影响的日期、地点和路线段。如果 B 改变了当天的主要停留区域，还要更新对应天气位置。

真正重算时，未受影响日期的路线与天气会被保留，只重新请求第二天相邻地点的路线和当天锚点位置的天气。提交前还会比较未受影响日期的规范化哈希，防止一次局部修改意外改动其他天。

对于改变总天数、删除必去地点或大幅改变路线等重要操作，系统不会直接覆盖当前版本，而是先保存提案并等待确认。确认以后创建一个新版本；拒绝则保留原版本。

撤销也属于这个循环的一部分。它不是删除最新记录，而是读取上一个版本的快照，再创建一个类型为 `undo` 的新版本。这样整个规划过程仍然可追踪。

## 六、循环能够恢复，靠的不只是 LangGraph

如果只看流程图，`interrupt()` 和 `Command(resume=...)` 好像已经解决了暂停恢复。真正做成 Web 产品后，还需要几层基础设施共同参与。

当前项目中：

- FastAPI 接收消息、校验恢复请求和返回工作流 ID；
- Celery 在后台执行耗时的模型、POI、路线和天气任务；
- PostgreSQL 保存路书版本、对话消息、工作流记录和 LangGraph checkpoint；
- Redis 作为 Celery Broker，并承载实时进度事件；
- SSE 将“理解需求”“等待补充”“生成推荐”“编排行程”等状态推送给前端；
- Next.js 工作台根据工作流状态展示问题卡、候选地点、规划进度和最终结果。

每次运行都有独立的 `workflow_run_id`，它同时用于关联业务记录、后台任务、日志和 LangGraph 的 `thread_id`。因此任务即使暂停，当前正式路书仍然可以正常读取；Worker 重启以后，也能根据检查点和业务状态继续。

这里还有一个容易踩坑的地方：LangGraph 的中断节点在恢复时会重新执行。所以暂停前的操作必须可重复，正式版本提交还要使用 `workflow_run_id` 做幂等约束。

当前项目还为循环加了几道保护：

- 同一个客户端消息重复发送时复用原工作流；
- 同一条补问回答重复恢复时不会重复合并；
- 同一个工作流只能提交一个正式版本；
- 基础版本已经变化时拒绝旧提案覆盖新版本；
- 外部依赖暂时失败时由 Celery 有界重试；
- 天气或部分路线失败时保留 `unverified` / `unavailable` 状态，而不是伪造结果。

这些机制不直接让 Agent 更聪明，却决定了循环能不能在真实系统里安全运行。

## 七、工作流循环最终实现了什么

回头看，循环机制在当前项目里并不是一个单独功能，而是把多个功能串成产品闭环的骨架。

它目前实现了：

1. **多轮需求收集**：保留已确认字段，只追问阻断规划的关键信息；
2. **工作流暂停与恢复**：用户回答补问或完成地点选择后，从原检查点继续；
3. **真实地点消歧**：遇到同名或语义不明确的 POI 时，由用户保留最终决定权；
4. **推荐反馈收敛**：接受、拒绝和替换会影响当前路书的后续候选；
5. **行程可行性修复**：在明确上限内自动调整分日和顺序，不能修复时返回真实冲突；
6. **持续编辑**：修改后仅重算受影响范围，并生成可追踪的新版本；
7. **重要修改确认**：预览与正式版本分离，确认前不改变当前路书；
8. **失败恢复与幂等**：重复消息、任务重投和 Worker 重启不会重复提交业务结果；
9. **实时进度展示**：前端能够知道工作流正在运行、等待用户、已经完成还是执行失败。

这也让我对 Agent 工作流有了一个新的理解：循环的价值不是让模型多思考几遍，而是让系统在每一轮都能明确回答三个问题——现在已经确认了什么、为什么不能继续、下一步由谁做决定。

## 八、这一阶段的体会

第二篇完成时，RouteBook Agent 已经能够把一句自然语言变成一份简单行程。但那更像一次成功的演示。

加入这些循环以后，系统才开始接近一个可以长期使用的规划工具：需求不完整可以继续问，地点不明确可以暂停选，推荐不合适可以反馈，路线不可行可以修复，行程生成后还可以继续修改。

更重要的是，每一次循环都不是让模型随意重写全部结果。模型负责理解语言，地图和天气接口提供事实，领域服务判断约束与影响范围，用户负责关键选择，工作流负责保存状态并安排它们按正确顺序发生。
